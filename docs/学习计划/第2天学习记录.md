这一篇不要一上来讲 `ModuleFactory`、`__import__`、全局变量。面试官更关心的是：**这个项目为什么能切换模型、Embedding、向量库，以及这种设计有什么风险。**

30 秒人话版：

> 这个项目把模型、Embedding、文件解析器和向量数据库都做成可配置组件。CLI 仍保留模块级对象以兼容简单调用；FastAPI 已改为应用生命周期内的版本化 runtime registry。每个请求按受信租户身份获取不可变 runtime 租约和 Collection 权限，因此可以快速换模型，也不会让并发热切换直接覆盖正在执行的请求。

## 1. 一条主线记住装配过程

```text
配置文件：写清楚“用哪个模型、向量模型、文件解析器、向量库”
（代码名：deepsearcher/config.yaml）
  ↓ 读取配置
配置对象：把 YAML 整理成 Python 可用的数据
（代码名：Configuration.load_config_from_yaml / provide_settings）
  ↓ 按 provider 名字创建真实组件
组件工厂：根据配置里的名字找到对应类并实例化
（代码名：ModuleFactory / __import__ / getattr）
  ↓ 统一装配
运行时组件：大模型、向量模型、文件解析器、网页抓取器、向量库
（代码名：llm / embedding_model / file_loader / web_crawler / vector_db）
  ↓ 注入到查询流程
默认查询入口：先选择搜索策略，再执行搜索
（代码名：RAGRouter → DeepSearch / ChainOfRAG）
  ↓ 旁路对照方案
基础 RAG 方案
（代码名：NaiveRAG）
```

读法：左边中文是你先要理解的工程动作；括号里的英文是源码名，面试官追问“代码里在哪”时再说。

不要只背“工厂模式”。真正要说清的是：**配置决定实现类，工厂负责构造，上层只依赖抽象接口，`init_config` 负责把依赖装配进 Agent。**

## 4. ModuleFactory 的核心机制

核心逻辑可概括为：

```python
class_name = config.provide_settings[feature]["provider"]
module = __import__(module_name, fromlist=[class_name])
class_ = getattr(module, class_name)
instance = class_(**config.provide_settings[feature]["config"])
```

本次运行验证：

```text
deepsearcher.llm.OpenAI                     → BaseLLM 子类
deepsearcher.embedding.OpenAIEmbedding      → BaseEmbedding 子类
deepsearcher.loader.file_loader.PDFLoader   → BaseLoader 子类
deepsearcher.vector_db.Milvus               → BaseVectorDB 子类
```

### 为什么这样设计

- Agent 不需要写 `if provider == ...`。
- 新增 provider 时，主要新增一个适配类和导出声明。
- 测试可以给 Agent 注入 mock LLM、Embedding 和 Vector DB。
- 同一份业务控制流可切换不同云模型或本地模型。

### 代价

- provider 是字符串，缺少静态检查。
- 类名、模块导出或构造参数拼错，要到运行时才失败。
- 所有 provider 必须遵循约定的构造方式与抽象接口。
- 动态导入问题比显式 import 更难被 IDE 提前发现。

本次把 LLM provider 在内存中改成 `MissingProvider`，工厂运行时得到：

```text
AttributeError: module 'deepsearcher.llm' has no attribute 'MissingProvider'
```

磁盘上的 `config.yaml` 没有修改。

## 6. “全局单例”要准确表述

当前并不是经典的 Singleton 类，而是 **Python 模块级全局实例**：

```python
llm = None
embedding_model = None
vector_db = None
default_searcher = None
naive_rag = None
```

`init_config()` 通过 `global` 直接替换它们。本次连续初始化两次，验证结果：

```text
llm_replaced: True
router_replaced: True
```

因此它们不是“永远只有一个对象”，而是“任一时刻模块暴露一组当前对象”。

### 本地项目为什么这样做

- 调用方可直接使用 `configuration.default_searcher`。
- 初始化代码短，适合单进程、单用户学习项目。
- 多个 Agent 很容易共享同一客户端。

### 旧实现的并发和多租户为什么危险

1. 请求 A 正在使用旧 LLM 时，请求 B 调用 `/set-provider-config/` 替换全局对象；不同阶段可能看到不同配置。
2. 所有租户共享同一个默认 Collection 和客户端，配置隔离与数据授权没有边界。
3. 多个 Uvicorn worker 各有自己的 Python 进程和全局对象，热更新不会自动同步。
4. 重复 `init_config` 会创建新客户端，但代码没有显式关闭旧客户端的统一生命周期。
5. 测试若修改模块全局状态而未恢复，可能互相污染。

### 当前落地方案

- FastAPI lifespan 创建 `RuntimeRegistry`，用 `Depends` 显式租借 runtime。
- SQLite 控制面保存租户活动版本，多个 worker 读取同一版本事实。
- 租户、模型策略、版本和 Collection 白名单进入 `RuntimeRequestContext`。
- 候选 runtime 先构建、再用期望版本做事务 CAS；失败候选不会生效。
- 旧请求继续持有旧版本，最后一个租约释放后才关闭旧向量客户端。
- 配置、模型策略和权限一起回滚；敏感配置只允许引用环境变量。

## 7. 抽象基类真正提供了什么

抽象层的价值不是“代码看起来面向对象”，而是稳定调用契约：

```text
BaseLLM.chat(messages) → ChatResponse(content, total_tokens)
BaseEmbedding.embed_query(text) → List[float]
BaseEmbedding.embed_documents(texts) → List[List[float]]
BaseEmbedding.dimension → int
BaseVectorDB.search_data(...) → List[RetrievalResult]
RAGAgent.retrieve(...) → results, token_usage, metadata
RAGAgent.query(...) → answer, results, token_usage
```

上层依赖这些形状，所以千问通过 `OpenAI` compatible adapter 接入时，RAG Agent 无需知道具体 HTTP SDK。

需要诚实说明：部分基类方法只有方法体/文档，没有严格使用 `@abstractmethod` 阻止不完整子类实例化，因此接口约束主要依赖约定和测试。

## 9. 核心面试题（优化版，先学这一组）

### 核心题 1：为什么要把模型、向量库和解析器做成可配置组件？

#### 一句话回答

配置化把“使用哪种实现”与业务流程分开，便于替换供应商和本地实验，但也会把错误推迟到启动或运行阶段。

#### 2～3 分钟回答

项目通过 YAML 描述 LLM、Embedding、Loader 和 VectorDB，再由配置对象和工厂创建具体实例。上层 Agent 依赖统一接口，不需要为每个供应商重写查询流程。这样适合学习和多环境切换；代价是模块名、类名、参数或接口约定写错时，静态检查不一定发现，往往到动态导入或初始化时才报错。因此生产上要补启动校验、配置版本和失败即停止，而不是带着半成品配置继续运行。

#### 面试官继续追问

- 配置化和硬编码相比，复杂度增加在哪里？
- 怎样在启动时发现类名或参数写错？
- 切换 Embedding 时为什么不能只改一行配置？

#### 当前项目证据

`deepsearcher/configuration.py` 读取配置并创建组件；`ModuleFactory` 根据模块和 provider 名动态取类；`init_config` 把组件装配进查询 Agent。

#### 诚实边界

当前项目能切换 provider，不代表任意实现都可无缝替换；构造参数、接口契约、向量维度和已有数据仍需兼容。

### 核心题 2：动态工厂和直接在代码里创建对象，应该怎样选择？

#### 一句话回答

实现种类少且稳定时直接实例化更清楚；需要按配置切换多个实现时工厂更灵活，但必须承担运行时校验成本。

#### 2～3 分钟回答

直接实例化的优点是 IDE 能跳转、类型错误更早暴露、调用链容易理解。动态工厂适合插件式 provider：配置决定模块，工厂负责定位类并传入参数，上层只面向抽象接口。当前项目选择动态方式，是为了支持不同模型、Embedding 和向量库。它的代价是隐式约定更多，调试也更难，所以我不会只说“用了工厂模式”，而会说明它解决了可替换性，同时带来运行时失败风险。

#### 面试官继续追问

- 如果 provider 数量只有两个，还值得用动态导入吗？
- 工厂返回了错误类型，怎样尽早发现？
- 依赖注入容器和当前工厂有什么区别？

#### 当前项目证据

把 LLM provider 临时改成不存在的名称时，工厂会在运行时失败；抽象基类测试用于约束各组件必须提供的能力。

#### 诚实边界

当前实现不是完整插件平台，也没有 provider 注册表、配置 Schema 和兼容性矩阵；扩展仍依赖代码约定。

### 核心题 3：全局配置为什么方便，又为什么不适合并发和多租户？

#### 一句话回答

全局对象减少传参和重复连接，但一次配置切换会影响整个进程，无法天然隔离不同请求和租户。

#### 2～3 分钟回答

当前初始化后，多个 Agent 共享同一组 LLM、Embedding 和 VectorDB，单用户本地演示很省事。但配置接口再次初始化时，会替换模块级对象；并发请求可能分别持有新旧实例，多 worker 之间又各有一份状态。多租户场景还需要独立的模型权限、Collection 范围和费用归属，单一全局配置做不到这些。更稳妥的方式是应用级客户端配合请求级依赖注入，租户身份和数据权限进入请求上下文。

#### 面试官继续追问

- 加一把线程锁能解决所有问题吗？
- 多进程 worker 为什么不会共享同一个 Python 全局变量？
- 旧客户端什么时候可以安全释放？

#### 当前项目证据

`init_config` 会重新创建并替换模块级对象；RAGRouter、DeepSearch、ChainOfRAG 和 NaiveRAG 共享装配出的依赖。本地实验也验证了二次初始化会替换对象。

#### 诚实边界

依赖注入、配置版本发布和租户隔离是建议的生产改造，当前仓库并未完整实现。

### 核心题 4：如何避免 API Key、配置内容和临时路径泄漏？

#### 一句话回答

敏感值只留在服务端，通过环境变量或密钥服务注入，并在日志、接口响应和 Trace 中做字段级脱敏。

#### 2～3 分钟回答

浏览器不应接触模型密钥；配置文件也不应提交真实 Key。服务端读取密钥后，只把必要配置传给客户端。日志需要区分可观测字段和敏感字段，禁止打印 Authorization、完整文件路径、原始 metadata 和用户文档内容。临时上传文件应使用受控目录、随机文件名、权限限制和及时清理。代价是调试信息会减少，因此要用请求 ID、错误码和脱敏摘要保留定位能力。

#### 面试官继续追问

- `.env` 文件为什么也可能泄漏？
- Trace 面板应该隐藏哪些内容？
- 多租户下怎样防止查询到别人的 Collection？

#### 当前项目证据

模型和向量库配置在服务端读取，浏览器经本地代理访问；上传代理会创建临时文件。但仓库当前更偏本地学习环境。

#### 诚实边界

当前项目没有完整的密钥托管、租户鉴权、审计和敏感数据分级方案，不能把“Key 没放前端”描述成安全体系已经完成。

## 9.1 源码细节补充题（第二遍再看）：全局配置为什么方便，又为什么伤害并发和多租户？

### 一句话回答

模块级全局对象让 CLI 调用简单、共享连接方便，但不能直接承担在线请求的版本与租户隔离；因此 FastAPI 使用请求租约和共享控制面，CLI 兼容层与在线架构分开。

### 2～3 分钟回答

`init_config` 仍可根据 YAML 通过 ModuleFactory 创建 LLM、Embedding、Loader 和 Milvus，并放入 `deepsearcher.configuration` 的模块级变量，供 CLI/库兼容调用。在线 API 不再从这些 globals 取对象，而是由 `RuntimeRegistry` 为请求提供同一版本下完整装配的组件。

旧问题是 `/set-provider-config/` 替换全局对象，多 worker 和并发请求无法形成一致快照。当前发布流程先构建候选 runtime，再把租户活动版本事务切换；各 worker 下一请求读取新版本，旧请求通过引用计数自然结束。Collection 由服务端白名单授权，调用方传参不能扩大权限。

该方案已在真实 `uvicorn --workers 2` 下验证发布和回滚。边界是当前控制面为共享 SQLite，适合同一部署；跨主机应迁移到 PostgreSQL 等共享事务数据库。

### 连续追问

- 加一把线程锁能解决吗？只能保护单进程切换瞬间，不能解决多进程同步、租户隔离和旧客户端生命周期。
- 多开 Uvicorn worker 会怎样？客户端仍按进程隔离，但活动版本与租户策略来自共享控制库；已验证两个 worker 发布和回滚结果一致。
- 为什么不每个请求创建 Milvus/LLM 客户端？隔离清楚，但连接和构造成本高；更合理的是应用级连接池加请求级不可变配置。

- `deepsearcher/runtime_registry.py::RuntimeControlStore`
