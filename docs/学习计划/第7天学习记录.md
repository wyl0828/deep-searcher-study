## 0. 面试官友好版：先讲“问题怎么找到答案”

这一篇尤其要降术语。不要先说 `RAGRouter`、`CollectionRouter`、`NaiveRAG`。先讲：**用户问问题后，系统怎么决定查哪里、怎么查、怎么生成答案。**

60 秒人话版：

> 用户提问后，系统不会直接让大模型凭记忆回答，而是先判断这个问题适合用哪种检索策略。简单问题可以做一次检索，复杂问题可能需要多轮搜索。确定策略后，系统再判断应该查哪个知识库，把用户问题转成语义向量，到向量数据库里找最相关的文档片段。找到片段后，再把这些片段作为上下文交给大模型生成答案。这样做的好处是答案更容易基于项目文档，而不是大模型凭空编；代价是路由、检索、上下文拼接每一步都可能出错，所以要做路由校验、空结果原因区分、召回评估和 token 成本控制。

术语降噪：

| 源码词 | 面试友好说法 |
| --- | --- |
| RAGRouter | 查询策略选择器 |
| CollectionRouter | 知识库选择器 |
| NaiveRAG | 最基础的一次检索方案 |
| DeepSearch | 多轮搜索方案 |
| ChainOfRAG | 逐步构造上下文的搜索方案 |
| RetrievalResult | 命中的文档片段 |
| TraceCollector | 执行过程记录器 |

面试官可能追问：

- 为什么不直接问大模型？
- 多个知识库时怎么判断查哪个？
- 路由选错会怎样？
- 没搜到结果能不能说明知识库没有答案？
- 为什么朴素 RAG 不够？

追问时再拿源码或证据：

- 默认查询入口会进入查询策略选择器，候选是 DeepSearch 和 ChainOfRAG。
- 朴素 RAG 是一次检索加一次生成，更适合作为 baseline。
- 知识库选择会按向量维度过滤 Collection，但仍缺少非法名称校验。
- Trace 是执行日志，不是模型思维链。

## 3. 用户问题进入系统后发生什么

如果要追代码，可以看：`deepsearcher/online_query.py`

### 默认查询

```python
def query(original_query: str, max_iter: int = 3):
    default_searcher = configuration.default_searcher
    return default_searcher.query(original_query, max_iter=max_iter)
```

这说明 `query()` 本身很薄，只是把问题交给全局装配好的 `default_searcher`。

当前 `default_searcher` 来自：

```python
default_searcher = RAGRouter(
    llm=llm,
    rag_agents=[
        DeepSearch(...),
        ChainOfRAG(...),
    ],
)
```

所以默认在线查询不是 NaiveRAG，而是：

```text
RAGRouter → DeepSearch 或 ChainOfRAG
```

### 带 Trace 查询

```python
def query_with_trace(original_query: str, max_iter: int = 3):
    collector = TraceCollector(original_query)
    answer, results, consume_tokens = default_searcher.query(
        original_query,
        max_iter=max_iter,
        trace_collector=collector,
    )
```

Trace 用来记录可观察执行阶段，例如选择了哪个 Agent、用了多少 routing token、最终检索结果等。

注意：

> Trace 不是模型思维链，不应该说它暴露了 LLM 内部推理。它只是项目自己记录的执行过程。

### NaiveRAG 查询

```python
naive_rag = configuration.naive_rag
answer, retrieved_results, consume_tokens = naive_rag.query(query)
```

`NaiveRAG` 是单独创建的，方便做朴素 RAG 对照，但它不在默认 `RAGRouter` 的候选 Agent 列表里。

## 4. 查询策略选择器负责什么

先用中文理解：它负责判断“这个问题适合哪种搜索方式”。括号里的 `RAGRouter` 是代码名，不是第一遍需要背的概念。

如果要追代码，可以看：`deepsearcher/agent/rag_router.py`

查询策略选择器（代码名：`RAGRouter`）路由的是：

```text
这个问题应该交给哪个 RAG Agent？
```

当前默认候选是：

```text
1. DeepSearch
2. ChainOfRAG
```

核心 prompt 要求 LLM 只返回一个 Agent index：

```text
Given a query, select only one agent ...
Only return one agent index number ...
```

然后源码把返回内容转成 int：

```python
selected_agent_index = int(self.llm.remove_think(chat_response.content)) - 1
selected_agent = self.rag_agents[selected_agent_index]
```

如果 LLM 没直接返回数字，代码会尝试找最后一个数字：

```python
selected_agent_index = int(self.find_last_digit(...)) - 1
```

### 面试要点

查询策略选择器的价值：

- 不同问题可以选择不同查询策略。
- 简单问题不一定需要复杂多轮搜索。
- 复杂问题可以交给更强的 Agent。

查询策略选择器的风险：

- LLM 输出非法 index 时，当前实现没有边界校验。
- 如果返回 `9`，但只有 2 个 Agent，可能触发 `IndexError`。
- 如果 prompt 被污染或模型输出不稳定，路由结果会不稳定。
- 当前路由没有评测指标，不能声称它总是选得最优。

诚实回答模板：

> RAGRouter 是一个 LLM-based router，优点是灵活，能按问题语义选 Agent；代价是输出需要校验。当前代码处理了“不是纯数字但末尾有数字”的情况，但没有完整处理越界 index，所以生产上应增加范围检查、默认 fallback 和路由评测。

## 5. 知识库选择器负责什么

先用中文理解：它负责判断“这个问题应该查哪些知识库”。括号里的 `CollectionRouter` 是代码名。

如果要追代码，可以看：`deepsearcher/agent/collection_router.py`

知识库选择器（代码名：`CollectionRouter`）路由的是：

```text
这个问题应该查哪些 Milvus Collection？
```

初始化时会按维度列出 Collection：

```python
self.vector_db.list_collections(dim=dim)
```

调用时也会再次按维度获取 Collection：

```python
collection_infos = self.vector_db.list_collections(dim=dim)
```

这和第 4/5 天学的维度一致性连起来了：

> 1024 维查询向量只应该查 1024 维 Collection。

### 三种特殊情况

| 情况 | 行为 |
| --- | --- |
| 没有 Collection | 返回 `([], 0)` |
| 只有一个 Collection | 直接返回它，不调用 LLM |
| 多个 Collection | 调用 LLM，从 collection name/description 中选择 |

源码中还有两个兜底：

```python
if not collection_info.description:
    selected_collections.append(collection_info.collection_name)

if self.vector_db.default_collection == collection_info.collection_name:
    selected_collections.append(collection_info.collection_name)
```

也就是说：

- 没有描述的 Collection 会被默认加入。
- default collection 会被默认加入。

### 风险边界

当前实现没有严格过滤 LLM 返回的非法 Collection 名称。比如 LLM 返回：

```python
["not_exist_collection"]
```

它可能会被放进 `selected_collections`，后续 `vector_db.search_data()` 查询不存在的 Collection，底层失败后可能变成空结果。

面试回答：

> CollectionRouter 提高了多知识库场景下的相关性，但它依赖 LLM 输出，所以要做结果校验。当前代码会兜底加入 default collection 和无描述 collection，但没有过滤非法 collection name，这是生产化要补的点。

## 6. 基础 RAG 方案的检索流程

先用中文理解：基础 RAG 就是“一次检索 + 一次回答”，它适合当对照组，不是复杂问题的最终方案。

如果要追代码，可以看：`deepsearcher/agent/naive_rag.py`

核心流程：

```text
query
  ↓
CollectionRouter.invoke(query, dim)
  ↓
selected_collections
  ↓
embedding_model.embed_query(query)
  ↓
vector_db.search_data(collection, vector, top_k, query_text=query)
  ↓
deduplicate_results()
```

源码片段：

```python
retrieval_res = self.vector_db.search_data(
    collection=collection,
    vector=self.embedding_model.embed_query(query),
    top_k=max(self.top_k // len(selected_collections), 1),
    query_text=query,
)
```

注意这里的 `top_k` 会按 Collection 数量分摊：

```text
单个 collection: top_k = 10
两个 collection: 每个 5
三个 collection: 每个 3
```

最后再去重：

```python
all_retrieved_results = deduplicate_results(all_retrieved_results)
```

去重依据是 `result.text`，不是 `id` 或 `reference`。

### 一个隐藏短板

`NaiveRAG.__init__()` 只有在 `route_collection=True` 时才创建：

```python
self.collection_router = CollectionRouter(...)
```

但 `retrieve()` 的 `else` 分支写的是：

```python
selected_collections = self.collection_router.all_collections
```

所以如果一开始构造 `NaiveRAG(route_collection=False)`，可能没有 `self.collection_router`。测试里是先用 `route_collection=True` 构造，再把属性改成 `False`，因此测试能过。

面试诚实边界：

> 当前 `route_collection=False` 路径存在设计瑕疵，生产上要么总是创建 collection_router，要么显式从 vector_db.list_collections() 获取全部 Collection。

## 7. 基础 RAG 方案的生成流程

检索完成后，`NaiveRAG.query()` 会构造 prompt：

```text
Original Query: {query}

Related Chunks:
<chunk_0>
...
</chunk_0>
```

如果 `text_window_splitter=True` 且命中结果有 `wider_text`：

```python
chunk_texts.append(chunk.metadata["wider_text"])
```

否则使用：

```python
chunk_texts.append(chunk.text)
```

这对应第 3 天讲过的设计：

- 检索时用较短的 `chunk.text` 保持精确。
- 生成时用更宽的 `wider_text` 给 LLM 上下文。

最后：

```python
char_response = self.llm.chat([{"role": "user", "content": summary_prompt}])
final_answer = char_response.content
```

token 统计：

```text
总 tokens = 路由/检索 tokens + LLM 生成 tokens
```

## 9. 核心面试题（优化版，先学这一组）

### 核心题 1：为什么不能用“一次检索、一次回答”解决所有问题？

#### 一句话回答

一次朴素 RAG 简单稳定，但复杂问题可能需要拆解、补充检索和停止判断，一轮召回未必覆盖全部证据。

#### 2～3 分钟回答

朴素 RAG 适合单一事实问题：问题向量化、top-k 检索、拼上下文、生成答案，成本和行为都容易预测。但多跳问题、比较题或信息分散的问题，一次查询可能只召回一部分证据。更复杂的 Agent 可以生成子查询并迭代补充，但会增加模型调用、Token、延迟和循环风险。因此正确做法不是一律使用复杂 Agent，而是保留 NaiveRAG 作为 baseline，用评测决定哪些问题值得升级策略。

#### 面试官继续追问

- Query Rewrite 一次就算 Agentic RAG 吗？
- 复杂 Agent 怎样设置停止条件？
- 如何证明多轮检索真的优于朴素 RAG？

#### 当前项目证据

`NaiveRAG` 只做一次检索和生成；默认查询候选则是 DeepSearch 和 ChainOfRAG。具体多轮算法将在后续学习日展开。

#### 诚实边界

当前还没有按问题类型比较三种策略的准确率、延迟和 Token，不能声称复杂 Agent 必然更好。

### 核心题 2：为什么用大模型做查询路由，非法输出怎样处理？

#### 一句话回答

大模型能按自然语言语义灵活选择策略，但输出不可靠，必须做 Schema、范围校验和默认回退。

#### 2～3 分钟回答

硬编码关键词成本低、确定性高，但规则多后维护困难，也难覆盖同义表达。LLM 路由能结合问题和 Agent 描述做选择，更适合开放语义；代价是可能返回文字、越界数字或不稳定结果。生产上应使用结构化输出，校验索引属于候选范围，失败时回退到安全 baseline，并记录路由输入摘要、输出、耗时和 Token，建立带标准路由标签的评测集。

#### 面试官继续追问

- 只有两个策略时，为什么不用规则？
- 回退到哪个 Agent 最安全？
- 路由准确率怎样定义？

#### 当前项目证据

当前 `RAGRouter` 会尝试从非纯数字输出中提取数字，但取到索引后缺少完整范围检查，越界时可能抛出 `IndexError`。

#### 诚实边界

结构化输出、完整 fallback 和路由评测是建议改造；当前代码只做了部分解析容错。

### 核心题 3：知识库路由失败，为什么可能伪装成“没有命中”？

#### 一句话回答

路由器可能给出不存在的 Collection，而向量库异常又可能被转换成空列表，最终表面上只剩“无结果”。

#### 2～3 分钟回答

知识库路由的输入是问题和 Collection 描述，输出应限定在当前可用集合中。当前实现会合并默认集合，却没有严格过滤所有非法名称。错误名称进入搜索后，底层失败可能返回空列表。更可靠的设计是在调用前做 allowlist 校验，区分“没有可用库”“搜索成功但无命中”和“存储调用失败”，并把错误状态传到 API 和 Trace。

#### 面试官继续追问

- 为什么默认 Collection 兜底仍不能解决问题？
- 多租户下 allowlist 从哪里来？
- Collection 描述写得不好会造成什么影响？

#### 当前项目证据

`CollectionRouter` 负责选择集合，`search_data()` 的部分异常路径会返回空列表；因此路由错误和真实无命中可能在上层表现相似。

#### 诚实边界

当前项目没有租户级 Collection 权限、路由准确率评测和完整错误分类。

### 核心题 4：怎样区分检索失败和生成失败？

#### 一句话回答

先检查标准证据是否进入命中片段；证据没进来是检索问题，证据正确但回答错误才主要是生成问题。

#### 2～3 分钟回答

排查时保存三个层次：路由选择、检索结果、最终回答。若选错 Collection 或正确片段不在 top-k，检查 query、Embedding、metric、过滤和路由。若片段正确且完整，模型却答错或加入无依据内容，再检查 Prompt、上下文顺序、模型参数和忠实度。还要单独识别系统异常，不能把向量库离线放进“检索质量差”。

#### 面试官继续追问

- 正确片段排在第十，但 top-k 为 5，算哪类问题？
- 如何评测回答是否忠于证据？
- 无答案问题应该让系统怎样响应？

#### 当前项目证据

查询结果包含支持文档和距离，Trace 能记录部分路由与执行事件；NaiveRAG 会把检索上下文交给 LLM 生成答案。

#### 诚实边界

当前没有自动的检索/生成归因器，也没有完整答案忠实度指标；仍需评测集和人工抽查。

### 核心题 5：Trace 为什么不能叫“大模型思维链”？

#### 一句话回答

Trace 是应用主动记录的执行事件和输入输出摘要，不是模型内部不可见的推理过程。

#### 2～3 分钟回答

项目可以记录选中了哪个 Agent、检索了哪些文档、耗时和 Token，这些属于可观测性。它能帮助定位路由、检索和调用问题，也适合前端展示。但模型内部如何形成答案并没有被系统真实读取，日志中的“步骤”也可能只是应用预定义流程。准确称呼应是执行 Trace、阶段日志或决策摘要，避免对外声称暴露了模型思维链。

#### 面试官继续追问

- Trace 中哪些内容可能泄露隐私？
- 为什么不记录完整 Prompt 和文档原文？
- 非流式 Trace 如何升级成 SSE？

#### 当前项目证据

`TraceCollector` 记录问题、Agent 选择、检索与最终结果等结构化事件，前端 `TracePanel` 展示的是这些事件。

#### 诚实边界

当前 Trace 主要在请求完成后返回，不是完整实时流；SSE、脱敏策略和长期追踪存储仍是后续能力。

## 9.1 源码细节补充题（第二遍再看）

### Q1：默认在线查询走 NaiveRAG 吗？

一句话回答：

> 不走。默认 `query()` 使用 `configuration.default_searcher`，它是 `RAGRouter`，候选 Agent 是 `DeepSearch` 和 `ChainOfRAG`。

深入回答：

> `NaiveRAG` 也会在 `init_config()` 中创建，但它是单独用于朴素 RAG 查询或对照实验的，不在默认 RAGRouter 的候选列表里。这个区别很重要，不能把 NaiveRAG 说成默认生产查询路径。

### Q2：RAGRouter 和 CollectionRouter 有什么区别？

一句话回答：

> RAGRouter 选“用哪个 Agent”，CollectionRouter 选“查哪些 Collection”。

深入回答：

> RAGRouter 的输入是问题和 Agent 描述，输出一个 Agent index；CollectionRouter 的输入是问题和 Collection name/description，输出 Collection name 列表。前者决定查询策略，后者决定知识库范围。

### Q3：为什么用 LLM 做路由？

一句话回答：

> 因为路由依据是自然语言语义，LLM 比硬编码关键词更灵活。

取舍：

> 好处是扩展 Agent/Collection 时不需要写大量规则；代价是输出不稳定、成本更高、需要校验。当前项目有 prompt 约束和部分 fallback，但缺少完整越界检查和路由评测。

### Q4：RAGRouter 输出非法索引会怎样？

一句话回答：

> 当前代码可能抛异常，因为它把 LLM 输出转成 index 后直接访问 `rag_agents[selected_agent_index]`。

深入回答：

> 代码处理了非纯数字情况，会尝试找最后一个数字，但没有检查 index 是否在合法范围内。如果只有 2 个 Agent，LLM 返回 9，就可能 `IndexError`。生产上应该做范围校验、默认 fallback、告警和路由日志。

### Q5：CollectionRouter 输出不存在的 Collection 会怎样？

一句话回答：

> 当前没有严格过滤，后续查询不存在 Collection 可能失败，并可能被向量库适配层转换为空结果。

深入回答：

> CollectionRouter 会把 LLM 返回的 selected_collections 与 default/no-description collection 合并，但没有只保留已知 Collection 的校验。因此非法名称可能进入 `search_data()`。这也是为什么空结果不一定等于知识库没有答案。

### Q6：NaiveRAG 为什么叫 naive？

一句话回答：

> 因为它只做一次检索和一次生成，不做多轮子查询、反思或迭代补充。

深入回答：

> NaiveRAG 的流程是问题 Embedding、向量检索、拼接上下文、LLM 总结回答。它简单、成本可控、容易作为 baseline；但复杂多跳问题可能召回不全，也不会根据中间结果改写查询。

### Q7：`wider_text` 在在线查询中怎么用？

一句话回答：

> 检索命中 Chunk 后，NaiveRAG 会优先把 `metadata["wider_text"]` 放进生成 prompt。

深入回答：

> 这样做是为了让检索保持精细，但生成时给 LLM 更完整上下文。测试里验证了 `text_window_splitter=True` 使用 `wider_text`，关闭后使用原始 `text`。

### Q8：为什么 top_k 要按 Collection 数量分摊？

一句话回答：

> 为了控制总召回数量和后续 prompt 大小。

深入回答：

> 如果选中多个 Collection，每个都返回完整 top_k，总上下文会迅速膨胀。当前实现用 `self.top_k // len(selected_collections)` 做简单分摊。代价是每个 Collection 分配固定名额，可能错过某个更相关 Collection 中排名靠后的结果。更好的方案是跨 Collection 统一重排。

### Q9：Trace 是不是模型思维链？

一句话回答：

> 不是。Trace 是项目记录的执行事件，不是模型内部思维链。

深入回答：

> `query_with_trace()` 用 `TraceCollector` 记录问题、选中 Agent、routing token、最终结果等。这对可观测性和前端展示很有用，但不能说它暴露了 LLM 的真实推理过程。

### Q10：NaiveRAG 的最大短板是什么？

一句话回答：

> 只检索一次，缺少查询改写、反思、重排和质量评估。

深入回答：

> 对简单事实问题，NaiveRAG 可以作为 baseline；但对复杂问题，它不知道是否漏召回，也不会基于第一轮结果生成子查询继续搜索。后续 DeepSearch/ChainOfRAG 就是为了解决这类问题，但它们也带来更高 token 成本和更复杂控制流。

## 10. 今天的 1 分钟表达模板

> 在线查询入口在 `online_query.py`。默认 `query()` 会调用全局的 `default_searcher`，它其实是 `RAGRouter`，当前候选 Agent 是 `DeepSearch` 和 `ChainOfRAG`，不是 NaiveRAG。RAGRouter 用 LLM 根据问题选择查询策略；具体 Agent 内部再通过 CollectionRouter 选择要查的 Milvus Collection。朴素 RAG 的流程是：先把用户问题做 `embed_query()`，再对选中的 Collection 调 `vector_db.search_data()`，拿到 `RetrievalResult` 后去重，把 `wider_text` 或 `text` 拼进 prompt，最后调用 LLM 生成答案。这个设计灵活，但路由依赖 LLM 输出，当前缺少完整非法 index 和非法 Collection 校验，所以生产上要加 fallback、日志和评测。
