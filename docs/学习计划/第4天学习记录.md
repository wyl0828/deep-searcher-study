## 0. 面试官友好版：先讲“文本怎么变成可比较的语义坐标”

这一篇不要先抛 `BaseEmbedding`、`embed_query`、`FLOAT_VECTOR`。先讲：**Embedding 是把文本变成一串数字，让系统能用距离比较语义接近程度。**

30 秒人话版：

> 文本本身不能直接做数学检索，所以系统会把每个文档片段和用户问题都转换成固定长度的数字向量。语义相近的文本，在向量空间里距离会更近。这里有两个关键点：第一，入库和查询必须使用同一个维度的向量，否则向量库没法比较；第二，项目默认用 L2 距离，距离越小代表越近，不能说分数越大越相似。Embedding 能帮助语义检索，但它不是事实校验器，最终答案还要看召回内容和生成质量。

术语降噪：

| 文档里会出现的词 | 面试时先翻译成 |
| --- | --- |
| Embedding | 语义向量 |
| dimension | 向量长度 / 维度 |
| embed_query | 把用户问题转成向量 |
| embed_documents | 把文档片段转成向量 |
| L2 | 欧氏距离 |
| Cosine | 方向相似度 |
| score/distance | 检索距离值，解释要看度量方式 |

面试官可能追问：

- 为什么维度必须一致？
- L2 距离和相似度有什么区别？
- 换 Embedding 模型要不要重新入库？
- Embedding 能不能保证答案正确？

追问时再拿源码或证据：

- 当前配置的 Embedding 维度是 1024。
- 向量库建表时会固定向量字段维度。
- 本次数学实验里，同方向但长度不同的向量 Cosine 是 1，L2 却很大。
- 维度不一致时，连基本距离计算都无法成立。

## 1. 今天先记住一条链路

```text
文档片段里的文字
  （代码名：chunk.text）
  ↓ 批量送去做语义向量化
  （代码名：BaseEmbedding.embed_chunks）
一批待向量化的文本
  （代码名：embed_documents(batch_text)）
  ↓ 当前向量模型生成数字向量

  （代码名：List[float]）

  （代码名：chunk.embedding）
  ↓ 用同样的维度存入向量库
向量库里的向量字段
  （代码名：Milvus FLOAT_VECTOR(dim=embedding_model.dimension)）
```

先按中文理解：文字不能直接数学检索，所以先变成固定长度的数字向量；括号里的英文是源码名。

> DeepSearcher 不直接把原始 PDF 写进向量库，而是先把文档切成 Chunk，再对 `chunk.text` 做 Embedding。Embedding 的结果是固定维度的浮点向量，Milvus Collection 建表时也会固定 `FLOAT_VECTOR(dim=...)`，所以查询向量和入库向量必须来自同一套维度配置，否则检索阶段无法比较。

## 3. 向量模型要会做的四件事

先用中文理解这四件事：**把一个问题变向量、把一批文档变向量、把片段批量补上向量、告诉系统向量有多长。**

如果要追代码，可以看：`deepsearcher/embedding/base.py`

`BaseEmbedding` 规定了四件事：

```python
embed_query(text: str) -> List[float]
embed_documents(texts: List[str]) -> List[List[float]]
embed_chunks(chunks: List[Chunk], batch_size: int = 256) -> List[Chunk]
dimension -> int
```

### `embed_query`

用于在线查询：

```text
用户问题
  ↓ embed_query
查询向量
  ↓ vector_db.search_data
检索相近 Chunk
```

### `embed_documents`

用于批量处理文档文本。基类默认实现只是循环调用 `embed_query()`：

```python
return [self.embed_query(text) for text in texts]
```

具体 provider 可以重写它，把多条文本一次性发给模型 API，减少请求次数。

### `embed_chunks`

这是离线入库最关键的一步：

```text
chunks
  ↓ 取出每个 chunk.text
batch_texts
  ↓ embed_documents
embeddings
  ↓ zip(chunks, embeddings)
chunk.embedding = embedding
```

也就是说，Embedding 阶段会修改 `Chunk` 对象本身：原来 `chunk.embedding` 是 `None`，执行后变成 `List[float]`。

### `dimension`

`dimension` 是向量维度，例如当前配置里是 1024：

```yaml
embedding:
  provider: "OpenAIEmbedding"
  config:
    model: "text-embedding-v4"
    dimension: 1024
```

它不是装饰信息，而是会影响 Milvus Collection 的 schema。

## 5. Milvus 为什么要求维度一致

如果要追代码，可以看：`deepsearcher/vector_db/milvus.py`

初始化 Collection 时：

```python
schema.add_field("embedding", DataType.FLOAT_VECTOR, dim=dim)
```

而入库流程传入的 `dim` 来自：

```python
vector_db.init_collection(
    dim=embedding_model.dimension,
    collection=collection_name,
)
```

这意味着 Collection 的向量字段从创建那一刻起就固定维度。假设 Collection 是 1024 维：

- 插入 1024 维向量：可以。
- 插入 1536 维向量：schema 不匹配。
- 用 1536 维查询向量搜索 1024 维 Collection：无法进行同一空间的距离计算。

一个非常朴素的数学实验也能说明这个问题：

```python
import numpy as np

query = np.array([1.0, 0.0, 0.0])
bad = np.array([1.0, 0.0])
np.linalg.norm(query - bad)
```

实际报错：

```text
ValueError: operands could not be broadcast together with shapes (3,) (2,)
```

真实向量库的报错不一定长这样，但本质一样：维度不同，向量空间不同，不能直接比较。

## 6. L2 距离不能随口叫“相似度”

Milvus 当前默认 metric 是：

```python
metric_type: str = "L2"
index_params.add_index(field_name="embedding", metric_type=metric_type)
```

L2 是欧氏距离，直觉是“两个点之间的距离”。对于 L2：

- 距离越小，向量越近。
- 距离越大，向量越远。

所以不能偷懒说：

> “score 越大越相似。”

在当前 Milvus 实现里，`RetrievalResult.score` 来自：

```python
score=b["distance"]
```

如果 metric 是 L2，这个 score 更准确地叫“距离值”，不是“越大越好”的相似度分数。

## 7. 本次数学实验记录

实验命令：

```powershell
@'
import numpy as np

query = np.array([1.0, 0.0, 0.0])
docs = {
    "same_direction": np.array([0.9, 0.0, 0.0]),
    "orthogonal": np.array([0.0, 1.0, 0.0]),
    "opposite": np.array([-1.0, 0.0, 0.0]),
    "long_same_direction": np.array([9.0, 0.0, 0.0]),
}

def l2(a, b):
    return float(np.linalg.norm(a - b))

def cosine(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

print("query_dim=", len(query))
for name, vec in docs.items():
    print(name, "dim=", len(vec), "l2=", round(l2(query, vec), 4), "cosine=", round(cosine(query, vec), 4))

try:
    bad = np.array([1.0, 0.0])
    print(l2(query, bad))
except Exception as exc:
    print("dimension_mismatch_error=", type(exc).__name__, str(exc))
'@ | uv run --frozen python -
```

实际结果：

| 向量 | L2 距离 | Cosine | 解释 |
| --- | ---: | ---: | --- |
| `same_direction` | 0.1 | 1.0 | 方向一致，距离也近 |
| `orthogonal` | 1.4142 | 0.0 | 方向垂直 |
| `opposite` | 2.0 | -1.0 | 方向相反 |
| `long_same_direction` | 8.0 | 1.0 | 方向一致，但长度差很多 |

重点观察：

> `long_same_direction` 和 query 的余弦相似度是 1.0，但 L2 距离是 8.0。

这说明：

- Cosine 更关注方向。
- L2 同时受方向和向量长度影响。
- 如果向量没有归一化，不同 metric 的排序可能不同。

## 8. CollectionRouter 和维度过滤

如果要追代码，可以看：`deepsearcher/agent/collection_router.py`

CollectionRouter 初始化和调用时都会使用维度：

```python
self.vector_db.list_collections(dim=dim)
```

Milvus 的 `list_collections(dim=dim)` 会检查每个 Collection 的 `embedding` 字段：

```python
if field_dict["name"] == "embedding" and field_dict["type"] == DataType.FLOAT_VECTOR:
    if field_dict["params"]["dim"] != dim:
        skip = True
```

这说明查询路由阶段也在避免跨维度检索。

面试表达：

> 项目不是只在写入时关心维度，查询路由也会按当前 Embedding 模型的维度过滤 Collection。这样可以避免 1024 维查询向量误查 1536 维 Collection。

诚实边界：

> 这个过滤依赖向量库能正确返回 Collection schema；如果底层连接失败或 schema 查询异常，当前实现会记录 critical 日志并返回空列表，上层可能表现为没有可检索 Collection。

## 11. 核心面试题（优化版，先学这一组）

### 核心题 1：Embedding 解决什么问题，又不能保证什么？

#### 一句话回答

Embedding 让文本可以按语义距离检索，但不能保证召回事实正确，更不能直接保证最终答案正确。

#### 2～3 分钟回答

文档片段和用户问题会被映射到固定长度的向量，同一向量空间中的近邻可作为候选证据。这比只匹配字面关键词更能处理同义表达。但向量只是模型学到的语义表示：专业术语、数字、否定关系和新领域都可能表示不好；即使召回正确，生成模型也可能误读。因此需要分别评测检索和回答，而不是用一次“答对了”证明 Embedding 好。

#### 面试官继续追问

- BM25 表现很好时还需要向量检索吗？
- 怎样判断错在 Embedding 还是生成模型？
- 为什么查询和文档要用同一套模型？

#### 当前项目证据

离线阶段对 `Chunk.text` 生成向量，在线阶段对用户问题生成查询向量，再由 Milvus 返回邻近片段。

#### 诚实边界

当前项目没有 Embedding 模型对比集、领域微调或混合检索评测，不能声称现用模型在所有文档上最优。

### 核心题 2：为什么入库向量和查询向量的维度必须一致？

#### 一句话回答

Collection 的向量字段在建表时固定维度，不同长度的向量既不属于同一数据结构，也无法计算对应坐标间的距离。

#### 2～3 分钟回答

项目创建 Collection 时使用当前 Embedding 的 dimension 定义 `FLOAT_VECTOR(dim=...)`。文档插入和问题查询都必须满足这个 schema。如果入库用 1024 维、查询换成 1536 维，Milvus 会拒绝操作。即使两个模型恰好维度相同，也不能自动认为语义空间兼容，因为坐标含义可能完全不同。

#### 面试官继续追问

- 维度相同但模型不同，旧数据能否继续用？
- 能不能通过截断 1536 维向量适配 1024 维表？
- 维度越高，检索效果一定越好吗？

#### 当前项目证据

当前配置维度为 1024；项目用 `embedding_model.dimension` 建表，并在 Collection 路由时按维度过滤。第 5 天的 2 维表配 3 维查询实验得到明确的 dimension mismatch。

#### 诚实边界

维度一致只是必要条件，不是效果保证；还要保证模型版本、预处理和距离度量一致。

### 核心题 3：L2、Cosine 和 IP 应该怎样选择？

#### 一句话回答

要根据模型训练方式和是否归一化选择，并按度量定义解释结果；当前 L2 是距离，越小越近。

#### 2～3 分钟回答

L2 比较绝对几何距离；Cosine 更关注方向；IP 关注内积，向量模长会影响结果。若向量已归一化，Cosine、IP 与 L2 的排序可能存在关系，但工程上仍应遵循模型建议并通过评测确认。项目当前使用 L2，因此返回字段即使叫 score，也不能讲成“越大越相似”。切换 metric 还要考虑索引和已有 Collection 的一致性。

#### 面试官继续追问

- 为什么两个同方向向量的 Cosine 很高，但 L2 可能很远？
- 向量归一化会改变什么？
- 修改 metric 后是否需要重建索引？

#### 当前项目证据

数学实验中 `[9,0,0]` 和 `[1,0,0]` 的 Cosine 为 1，但 L2 距离为 8；真实 Milvus 实验也显示 L2 结果按 `0.01/0.81/4.81` 从近到远。

#### 诚实边界

当前项目没有对 L2、Cosine 和 IP 做统一离线评测，所以只能准确解释当前配置，不能宣称 L2 一定最佳。

### 核心题 4：为什么切换 Embedding 模型通常需要重建知识库？

#### 一句话回答

模型变化会改变维度或整个语义空间，旧文档向量不能与新查询向量可靠比较。

#### 2～3 分钟回答

切换时要检查模型名称、版本、维度、归一化方式和推荐 metric。维度不同会直接违反 schema；维度相同也可能处于不同语义空间。稳妥做法是新建版本化 Collection，重新解析或复用 Chunk、重新生成向量、做回归评测，再把查询流量切到新版本，保留回滚能力。代价是重新计算和双份存储成本。

#### 面试官继续追问

- 怎样做到不停机迁移？
- Chunk 不变时可以只重算向量吗？
- 如何判断新模型值得迁移？

#### 当前项目证据

`force_new_collection=True` 可以重建表，但会删除旧数据；现有配置没有完整记录 Embedding 版本与数据版本的绑定关系。

#### 诚实边界

蓝绿 Collection、版本治理和自动回滚是建议方案，当前仓库没有完整实现。

## 11.1 源码细节补充题（第二遍再看）

### Q1：Embedding 到底是什么？

一句话回答：

> Embedding 是把文本映射成固定维度的浮点向量，让语义相近的文本在向量空间里更接近。

深入回答：

> 在本项目里，离线阶段对 `Chunk.text` 做 Embedding，把结果写到 `chunk.embedding`；在线阶段对用户问题做 `embed_query()`，得到查询向量；然后 Milvus 根据向量距离召回相近 Chunk。Embedding 不是把文本压缩成可逆编码，而是为了语义检索服务的向量表示。

源码证据：

> `BaseEmbedding.embed_chunks()` 取出每个 `chunk.text`，调用 `embed_documents()`，再把结果赋值给 `chunk.embedding`。

诚实边界：

> 不能说 Embedding 一定理解事实真假，它只是语义表示；事实判断还要靠检索内容、提示词和 LLM 生成。

### Q2：为什么 Embedding 维度必须和 Collection 一致？

一句话回答：

> 因为 Milvus 的 `FLOAT_VECTOR` 字段在建表时固定了维度，不同维度的向量不能在同一个向量空间里比较。

深入回答：

> 项目入库时用 `embedding_model.dimension` 调用 `vector_db.init_collection()`，Milvus schema 中 `embedding` 字段会创建成 `FLOAT_VECTOR(dim=...)`。后续插入和查询都必须使用同样维度的向量。比如当前配置是 1024 维，如果换成 1536 维模型但继续写旧 Collection，就会出现 schema 不匹配或查询失败。

设计取舍：

> 维度固定让索引结构明确、检索高效；代价是切换 Embedding 模型时通常要重建 Collection 并重新入库。

### Q3：L2 距离能不能叫相似度？

一句话回答：

> 严格说不应该直接叫“相似度越大越好”，L2 是距离，通常越小越近。

深入回答：

> 当前 Milvus 默认 metric 是 `L2`，搜索结果里的 `score` 实际来自 Milvus 返回的 `distance`。如果 metric 是 L2，值越小代表越接近；如果是 IP 或 Cosine，解释方式又不同。所以面试时我会说“检索分数/距离值”，并根据 metric 解释排序含义。

容易被追问的点：

> 本次数学实验里，`[9,0,0]` 和 `[1,0,0]` 的 Cosine 是 1，但 L2 距离是 8，说明不同距离度量会产生不同解释。

### Q4：切换 Embedding 模型要注意什么？

一句话回答：

> 要检查维度、距离度量、旧数据是否重建，以及查询和入库是否使用同一个模型。

深入回答：

> 如果从 1024 维模型换到 1536 维模型，旧 Collection 的 `FLOAT_VECTOR(dim=1024)` 不能直接复用。正确做法通常是新建 Collection 或强制重建，把文档重新切分、重新 Embedding、重新写入 Milvus。同时要确认在线查询使用的新 Embedding 与入库使用的新 Embedding 一致，否则召回质量会严重下降。

诚实边界：

> 当前项目没有自动做 Embedding 模型迁移，也没有为 Collection 记录完整的模型版本治理。

### Q5：为什么要批量 `embed_chunks()`？

一句话回答：

> 批量可以减少 API 调用次数，提高吞吐，并让入库流程更可控。

深入回答：

> `embed_chunks()` 会按 `batch_size` 把 Chunk 文本分批送入 `embed_documents()`。对于远程 Embedding 服务，批量调用通常比逐条调用更省请求开销。不过 batch 太大可能触发 provider 的 token、条数或请求体限制，所以当前默认 `batch_size=256` 是吞吐和限制之间的折中。

源码证据：

> `tests/embedding/test_base.py` 验证了 3 个 Chunk、`batch_size=2` 时，`embed_documents()` 会被调用两次：第一次 2 条，第二次 1 条。

### Q6：Milvus、FAISS、pgvector 怎么取舍？

一句话回答：

> Milvus 更偏专用向量数据库，适合规模化向量检索；FAISS 更像本地向量索引库；pgvector 适合已经以 PostgreSQL 为主的小中规模业务。

深入回答：

> Milvus 提供 Collection、schema、索引、过滤、混合检索等数据库能力，适合服务化部署和较大规模检索。FAISS 性能强、适合本地或嵌入式向量索引，但数据库能力和服务治理要自己补。pgvector 的优势是和 Postgres 数据放在一起，事务和业务查询方便，但超大规模向量检索和专用索引能力通常不如专门向量数据库。当前项目选 Milvus，是因为 DeepSearcher 本身面向 RAG 检索，并且源码已经围绕 Collection、metadata、hybrid search 做了适配。

诚实边界：

> 当前学习环境不等于生产压测结果，不能夸大说 Milvus 在所有场景都优于 pgvector 或 FAISS。
