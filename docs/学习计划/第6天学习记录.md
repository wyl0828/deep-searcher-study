## 0. 面试官友好版：先讲“知识怎么进系统”

这一篇本来就是复盘，但仍然要避免一口气堆 `Document/Chunk/Embedding/Collection`。你先讲业务链路：**一份 PDF 进来，系统怎么把它变成以后能被问题搜到的知识。**

60 秒人话版：

> 这个项目的离线入库可以分成四步。第一步是解析，把 PDF 里的文字提取出来，并记录来源文件。第二步是切分，把长文档切成适合检索的小片段，同时保留片段附近的上下文。第三步是向量化，把每个片段变成固定维度的语义向量。第四步是写入向量数据库，把向量、文本、来源和附加信息一起保存。这样用户提问时，系统就能把问题也转成向量，在知识库里找最相关的片段，再交给大模型回答。这个方案比直接问大模型可靠，因为答案有文档依据；但它依赖解析质量、切分参数、向量模型、检索效果和异常处理，所以还需要评测和生产化改造。

## 2. 一分钟讲清离线入库

> DeepSearcher 的离线入库从配置开始。`config.yaml` 里声明 LLM、Embedding、Loader 和 VectorDB 的 provider，`ModuleFactory` 通过动态导入把字符串 provider 创建成真实对象。入库时，`load_from_local_files()` 先用 `PDFLoader` 把 PDF/TXT/MD 转成 LangChain `Document`，其中 `page_content` 是全文，`metadata["reference"]` 是来源路径。然后 `split_docs_to_chunks()` 用默认 `1500/100` 把文档切成 `Chunk`，并在 metadata 里加入 `wider_text` 上下文窗口。接着 `embedding_model.embed_chunks()` 对 `chunk.text` 做 Embedding，把固定维度向量写回 `chunk.embedding`。最后 Milvus 用 `embedding_model.dimension` 创建 `FLOAT_VECTOR(dim=...)` 的 Collection，并写入向量、文本、来源和 metadata。这个设计把解析、切分、向量化、存储解耦；短板是 PDF 解析较轻量、异常处理会吞掉部分底层错误、Embedding 模型版本治理还不完整。

## 3. 三分钟白板讲解结构

### 第 1 段：配置如何变成对象

```text
YAML provider 字符串
  ↓
__import__ + getattr
  ↓
真实模块实例
  ↓
注入 Agent / Loader / VectorDB
```

你要讲的重点：

- 这是“配置驱动 + 工厂构造”，不是硬编码 provider。
- 好处：方便切换千问、OpenAI-compatible Embedding、Milvus 等实现。
- 代价：provider 拼错、构造参数不匹配，要运行时才暴露。
- 并发短板：全局配置对象适合学习和单租户 demo，不适合多租户生产隔离。

源码证据：

- `deepsearcher/configuration.py`
- `deepsearcher/config.yaml`

### 第 2 段：文件如何变成 Chunk

```text
PDF
  ↓ pdfplumber.extract_text()
Document
  ↓ RecursiveCharacterTextSplitter
Chunk
```

你要讲的重点：

- 当前 `PDFLoader` 是“一份 PDF 一个 Document”，不是“一页一个 Document”。
- `Document` 是原始解析后的全文和来源。
- `Chunk` 是检索单元，包含 `text`、`reference`、`wider_text`。
- `chunk_size` 影响召回颗粒度和成本。

实验依据：

- `aurora-facts.pdf`：209 字符，默认 1 个 Chunk。
- `WhatisMilvus.pdf`：10672 字符，默认 `1500/100` 切成 10 个 Chunk，`500/50` 切成 25 个 Chunk。

### 第 3 段：Chunk 如何变成可检索向量

```text
Chunk.text
  ↓ Embedding
List[float]
  ↓ chunk.embedding
Milvus FLOAT_VECTOR
```

你要讲的重点：

- Embedding 不是压缩文本，也不是事实验证器，而是语义向量表示。
- 当前配置使用 OpenAI-compatible 的 `OpenAIEmbedding` 适配类，模型是 `text-embedding-v4`，维度是 1024。
- Milvus Collection 的 `FLOAT_VECTOR(dim=...)` 必须和 Embedding 维度一致。
- 当前默认 L2 是距离，不能说“score 越大越相似”。

实验依据：

- 2 维临时 Collection 中，查询 `[0.9, 0.0]` 命中 `[1.0, 0.0]`，distance 为 `0.01`。
- 3 维向量查询 2 维 Collection 会报 `vector dimension mismatch`。

## 6. 核心面试题（优化版，先学这一组）

### 核心题 1：请用一分钟讲清“知识如何进入系统”

#### 一句话回答

系统把原始文件解析成文本，切成可检索片段，转换成语义向量，再把向量、文本和来源一起写入向量数据库。

#### 2～3 分钟回答

解析解决“从文件里拿到什么内容”；切分解决“用多大颗粒度检索”；Embedding 解决“如何比较语义接近程度”；Milvus 解决“如何持久化并查找近邻向量”。四层拆开后，解析器、向量模型和存储都可以独立替换。代价是每层都会引入误差：解析可能丢结构，切分可能割裂语义，Embedding 可能表示不准，向量库异常还可能被误判成无命中。

#### 面试官继续追问

- 为什么不让大模型直接读取整份 PDF？
- 哪一步最影响引用准确性？
- 哪些组件更换后必须重新入库？

#### 当前项目证据

第 3 天完成解析与切分实验，第 4 天验证维度和距离，第 5 天完成真实 Collection 建表、插入和搜索。

#### 诚实边界

当前链路已在本地跑通，但缺少系统检索评测、页码引用、批量任务恢复和生产级权限控制。

### 核心题 2：回答质量差时，怎样判断问题出在解析、切分、向量化还是检索？

#### 一句话回答

从最终答案反向追到命中片段，再逐层检查“原文是否存在、片段是否完整、向量是否召回、检索是否正常”。

#### 2～3 分钟回答

先判断标准事实是否真的在源文件；若解析文本中没有，问题在 Loader。原文存在但被切断或 metadata 丢失，问题在切分。正确片段完整存在却进不了 top-k，需要比较 Embedding、query 表达、metric 和索引。若请求报错或返回空列表，还要排除 Collection 路由、维度和 Milvus 连接。只有检索证据正确而最终答案仍错，才优先检查 Prompt 和 LLM。

#### 面试官继续追问

- 怎样区分“Embedding 不好”和“top-k 太小”？
- 命中片段正确，为什么回答仍可能错误？
- 解析质量用什么指标衡量？

#### 当前项目证据

学习记录已保存原始字符数、Chunk 数、向量维度、L2 距离和故障实验；这些数据能定位链路边界，而不只看最终回答。

#### 诚实边界

当前 Trace 尚未覆盖所有解析和检索中间量，排查仍需结合日志、脚本和数据库检查，不是完整的一键诊断系统。

### 核心题 3：如何建立一套最小可用的离线检索评测？

#### 一句话回答

准备带标准证据片段的问题集，固定变量后计算 Recall@K，并同时记录空结果率、延迟、重复率和失败类型。

#### 2～3 分钟回答

先从真实文档人工整理 30～50 道问题，覆盖事实、同义表达、跨段和无答案场景，为每题标注相关页或 Chunk。然后分别运行不同切分参数、Embedding、metric 和 top-k，计算标准证据是否进入前 K。检索评测与生成评测要分开：Recall@K 高只能说明证据被找回，不能证明答案忠实。每次实验还要保存配置版本和数据版本，保证结果可复现。

#### 面试官继续追问

- Precision@K 和 Recall@K 怎样取舍？
- 无答案问题怎么评测？
- 评测集太小会产生什么偏差？

#### 当前项目证据

现有链路已经能返回检索片段、来源和距离，也能切换 chunk 参数，具备搭建最小评测脚本所需的输入和输出。

#### 诚实边界

当前项目还没有这套标注集和自动指标，不能用单次演示结果代替检索质量结论。

### 核心题 4：当前离线入库最大的三个技术债是什么？

#### 一句话回答

缺少结构化文档解析与精确引用、缺少可重复检索评测、异常与数据版本管理不完善。

#### 2～3 分钟回答

第一，默认 PDF 解析只处理文本层，页码、表格、图片和扫描件支持不足。第二，切分、Embedding 和 metric 主要依据默认配置，没有 Recall@K 等评测闭环。第三，Embedding 版本与 Collection 没有完整绑定，重建可能删除旧数据，向量库异常又可能变成空结果。优先级上我会先补评测和错误分类，因为没有度量就无法证明后续解析或检索优化有效。

#### 面试官继续追问

- 为什么先补评测，而不是先上 Rerank？
- 三项技术债中哪一项最影响用户信任？
- 如何分阶段改造而不停止现有查询？

#### 当前项目证据

第 3～5 天分别验证了无页码引用、无 Embedding 版本治理、`force_new_collection` 删除风险和异常转空列表等问题。

#### 诚实边界

混合检索、Rerank、版本化 Collection 和引用校验属于后续路线，目前不能写成已实现亮点。

## 6.1 源码细节速答卡（第二遍再看）

### 1. 为什么不用整篇 PDF 直接做 Embedding？

一句话：

> 整篇做 Embedding 颗粒度太粗，容易超过模型输入限制，也会增加 LLM 上下文成本。

深入回答：

> RAG 需要召回和问题最相关的局部片段。如果整篇 PDF 只有一个向量，用户问一个细节也只能召回整篇，既不精准，也浪费 token。当前项目先用 Loader 得到 `Document`，再用 splitter 切成 Chunk；Chunk 是实际 Embedding 和检索单元。代价是 Chunk 太小会丢上下文，所以项目用 overlap 和 `wider_text` 缓解边界问题。

诚实边界：

> 当前项目没有自动评测最优 chunk_size，默认 `1500/100` 是经验参数。

### 2. `Document` 和 `Chunk` 有什么区别？

一句话：

> `Document` 是 Loader 解析后的文档对象，`Chunk` 是后续 Embedding 和检索使用的切分单元。

源码证据：

> `PDFLoader.load_file()` 返回 `Document(page_content, metadata["reference"])`；`split_docs_to_chunks()` 返回 `Chunk(text, reference, metadata["wider_text"])`。

### 3. 为什么 `metadata["reference"]` 重要？

一句话：

> 它保留来源，检索命中后可以告诉用户答案来自哪个文件或 URL。

深入回答：

> 如果没有 reference，LLM 可以生成答案，但系统无法解释证据来源，也不方便调试错误召回。当前项目 reference 主要是文件路径，还没有页码级引用，这是一个边界。

### 4. 为什么 Embedding 维度必须一致？

一句话：

> 因为 Collection 的 `FLOAT_VECTOR(dim=...)` 在建表时固定了维度，不同维度的向量不能比较。

实验依据：

> 本次 2 维 Milvus Collection 用 3 维向量搜索，Milvus 直接报 `vector dimension mismatch`。

### 5. L2 distance 能叫相似度吗？

一句话：

> 严格说不应该，L2 是距离，通常越小越近。

深入回答：

> 项目里 `RetrievalResult.score` 填的是 Milvus 返回的 `distance`。如果 metric 是 L2，score 其实是距离值；如果换成 Cosine 或 IP，解释方式又不同。所以面试时要按 metric 解释，不能笼统说“分数越大越好”。

### 6. 为什么选择 Milvus？

一句话：

> 因为项目核心是 RAG，需要专门的高维向量检索、Collection 管理、metadata 返回和可扩展检索能力。

取舍：

> FAISS 更轻量，适合本地索引；pgvector 适合已有 PostgreSQL 的小中规模业务；Milvus 更像专门向量数据库，但引入了独立服务和运维成本。

### 7. Milvus Lite 和 Docker Milvus 怎么选？

一句话：

> Lite 适合本地轻量 demo，Docker standalone 更接近服务化部署。

本项目证据：

> Docker Milvus 实验通过；但仓库里的 `tests/vector_db/test_milvus.py` 使用 `uri="./milvus.db"` 会走 Milvus Lite，当前环境缺少 `milvus_lite` 包导致 6 个测试失败。

### 8. `force_new_collection=True` 为什么危险？

一句话：

> 因为它会 drop 已有 Collection 再重建，可能删除已有向量数据。

深入回答：

> 本地实验中它很方便，可以清掉旧 schema；生产中必须有权限、备份和迁移流程。当前项目没有防误删保护。

### 9. Milvus 返回空结果是不是说明知识库没答案？

一句话：

> 不一定，可能是知识库真没答案，也可能是连接失败、维度不匹配、Collection 路由错误或检索参数问题。

深入回答：

> 当前 `search_data()` 捕获异常后返回空列表，`list_collections()` 失败也可能返回空列表。因此“空结果”不能直接等同“无答案”。生产上应该区分系统错误、无 Collection、无命中和低置信度命中。

### 10. 当前离线入库最大的三个技术债是什么？

一句话：

> PDF 解析轻量、缺少检索评测、异常与数据治理不够细。

展开：

1. PDF：没有 OCR、页码级引用、复杂表格和版面理解。
2. 评测：没有系统化的召回率、答案准确率、延迟和成本评测。
3. 治理：Embedding 模型版本、Collection 迁移、异常上抛和多租户隔离不足。

## 7. 你不能说错的事实清单

- 当前默认 Loader 是 `PDFLoader`。
- `PDFLoader` 支持 PDF、TXT、Markdown。
- 当前 PDF 解析是一份 PDF 一个 `Document`。
- `Document` 的来源存在 `metadata["reference"]`。
- 默认切分参数是 `chunk_size=1500`、`chunk_overlap=100`。
- `wider_text` 是 Chunk 周围上下文窗口，不是 Embedding 文本本身。
- 当前 Embedding 配置是 `OpenAIEmbedding` 适配类，模型 `text-embedding-v4`，维度 1024。
- `OpenAIEmbedding` 不等于一定调用 OpenAI 官方服务；它可走 OpenAI-compatible API。
- Milvus 默认 URI 是 `http://127.0.0.1:19530`。
- Milvus 默认 metric 是 `L2`。
- 当前 `RetrievalResult.score` 填的是 Milvus 的 `distance`。
- L2 distance 通常越小越近。
- 当前项目没有完整 OCR、页码引用、检索评测、生产鉴权、限流、多租户。
