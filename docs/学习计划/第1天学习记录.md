## 0. 先理解：这个项目解决什么问题

这一篇不要一上来讲端口、容器、类名。项目面试通常会先问：**这个项目解决什么问题、整体链路是什么、为什么使用 RAG，以及你实际做了哪些工作。**

30 秒人话版：

> DeepSearcher 是一个基于 RAG 的文档问答项目。用户先上传 PDF，系统把文档解析、切分并向量化后写入 Milvus；用户提问时，系统从知识库检索相关片段，再交给千问生成答案。为了方便理解和演示，我补充了中文可视化前端，用流程面板展示入库、路由、检索和回答结果。当前链路已能本地运行，但检索评测、错误分类、流式输出和生产安全仍需完善。

术语降噪：

| 文档里会出现的词 | 面试时先翻译成 |
| --- | --- |
| FastAPI | 后端接口服务 |
| Frontend/BFF | 前端页面和本地代理 |
| Milvus | 向量数据库 |
| Collection | 一组可检索的知识库数据 |
| TracePanel | 页面上的流程观察面板 |

- 项目中遇到过什么实际问题，你是怎么定位的？

追问时再拿源码或证据：

- 运行端口：前端 `8600`、后端 `8100`、Milvus `19530`。
- 实测入库：`WhatisMilvus.pdf` 入库到 `day1_milvus`，行数为 10。
- 实测查询：Project Aurora 问题返回负责人和上线日期。

### 三个端口必须会解释

| 端口 | 进程 | 职责 | 停止后的现象 |
| --- | --- | --- | --- |
| 8600 | `frontend.server:app` | 向浏览器提供 React 页面，并代理上传、查询和健康检查 | 页面无法访问 |
| 8100 | `main:app` | 执行 DeepSearcher 入库、Agent 路由、检索和回答 | 8600 仍可访问，但查询返回 503 |
| 19530 | Docker Milvus | 保存 Collection、向量、文本和 metadata，执行向量检索 | 健康页显示 Milvus 离线，检索不可用 |

原计划使用 8500，但本机 Windows 当前排除了 TCP `8432–8531`，8500 绑定会触发 `WinError 10013`，因此本次改用 8100。端口是部署参数，不是业务逻辑。

## 3. 离线入库实测

使用仓库公开样例 `examples/data/WhatisMilvus.pdf`，通过 8600 的 `/api/ingest` 写入 `day1_milvus`。

```text

  → 8600 校验 PDF、Collection 名称并写临时目录

  → PDFLoader / pdfplumber

  → text-embedding-v4（1024 维）
  → Milvus day1_milvus（10 个 Chunk）
```

### 入库过程中遇到的两个环境问题

1. Docker 只有 1 GB 内存，Milvus RocksDB 写入时报 `Cannot allocate memory`。将 `C:\Users\32957\.wslconfig` 的 `memory` 调到 4 GB 并重启 Docker 后解除。
2. Windows 把 9000/9001 纳入动态排除范围，MinIO 无法重新发布到主机。Milvus 只需要容器内部的 `minio:9000`，因此使用 Git 已忽略的 `logs/day1-compose-no-minio-ports.yml` 取消 MinIO 主机端口发布。

启动命令：

```powershell
docker compose `
  -f infra/milvus/docker-compose.yml `
  -f logs/day1-compose-no-minio-ports.yml `
  up -d
```

## 4. 在线查询实测

### 查询 A：Project Aurora 多事实问题

问题：`Project Aurora 的负责人和批准上线日期是什么？`

| 指标 | 结果 |
| --- | --- |
| 最终答案 | 负责人 Lin Qiao；批准上线日期 2026 年 9 月 15 日 |
| Agent | `ChainOfRAG` |
| 实际迭代 | 3 轮 |
| 采用文档 | 1 条：`aurora-facts.pdf` |
| 延迟 | 18.24 秒 |
| 总 Token | 2175 |

三轮子查询分别是：

1. `Project Aurora 的负责人是谁？`
2. `Project Aurora 的批准上线日期是什么？`
3. `Project Aurora 的负责人和批准上线日期分别是什么？`

结论：ChainOfRAG 确实按中间结果逐步补信息，但 `early_stopping=False` 时会跑满 3 轮，第三轮存在重复倾向。

### 查询 B：新入库的 Milvus 文档

问题：`What is Milvus and what is it designed for?`，`max_iter=1`。

| 指标 | 结果 |
| --- | --- |
| Agent | `DeepSearch` |
| 采用文档 | 6 条 |
| 延迟 | 77.45 秒 |
| 总 Token | 19,942 |
| Trace 迭代 | 0 轮 |

结论：回答覆盖 Milvus 的向量数据库定位、ANN、扩展性和应用场景，但过长、成本过高。`DeepSearch` 虽然完成检索，当前结构化 Trace 尚未接入其逐轮细节，所以 Trace 为 0 轮；这不是“没有执行检索”。

## 5. 故障实验

### FastAPI 离线

停止 8100 后再次查询：

- 8600 页面仍可访问。
- `/api/query` 返回 HTTP 503。
- 页面显示“FastAPI 当前不可用，请先启动后端服务”。
- 在线查询流程节点统一显示“执行失败”。

说明 8600 是独立 BFF，能够把连接错误映射成用户可读信息。

### Milvus 离线

停止 Compose 后访问 `/api/health`：

- FastAPI：在线。
- Milvus：离线。
- LLM / Embedding：已配置。

“已配置”只说明模型配置存在，不代表向量库可用。当前 Milvus 健康检查仅探测 19530 TCP，端口打开时内部 Proxy 仍可能未 ready；生产环境还应执行语义级 readiness 检查。

## 6. 今日发现的技术债

1. 页面把默认 L2 `distance` 标为“相似度”，语义不严谨。
2. `ChainOfRAG` 默认关闭 early stopping，可能产生重复轮次和额外 Token。
3. `DeepSearch` 的结构化 Trace 没有逐轮接入。
4. 健康检查只探测 Milvus TCP，不能证明 Proxy/DataCoord/QueryCoord 已 ready。
5. Milvus wrapper 会捕获部分插入异常，上层存在返回“入库成功”但实际未写入的风险。
6. DeepSearch 即使 `max_iter=1` 也可能产生很高的 Token 和延迟，需要评测与预算限制。

## 7. 一分钟口述模板

> 浏览器访问 8600，它既提供 React 页面，也是本地 BFF，负责 PDF 校验、临时文件和错误映射；BFF 再调用 8100 的 DeepSearcher FastAPI。离线入库时，PDF 被解析成文本，按 1500/100 切成 Chunk，用 text-embedding-v4 生成 1024 维向量后写入 19530 的 Docker Milvus。在线查询时，RAGRouter 选择 DeepSearch 或 ChainOfRAG，再做 Collection 路由、向量检索和千问回答。今天我实际写入了 10 个 Chunk，并跑通两个真实查询；同时验证了后端和 Milvus 离线时的行为。当前系统仍有 L2 标注、假健康、异常吞掉和 Token 成本偏高等技术债。

## 8. 核心面试题（优化版，先学这一组）

### 核心题 1：请介绍一下这个项目，它解决了什么问题？

#### 一句话回答

这是一个基于 RAG 的文档问答项目，让大模型先从用户知识库检索证据，再基于证据回答问题。

#### 2～3 分钟回答

项目解决的是通用大模型不了解私有文档、回答缺少依据的问题。离线阶段把 PDF 解析、切分、向量化后写入 Milvus；在线阶段把用户问题向量化，检索相关片段，再由千问结合上下文生成答案。前端负责上传、提问和展示执行过程，FastAPI 负责业务编排。与普通聊天相比，它的优势是能使用用户文档；代价是答案质量受到解析、切分、检索和生成多个环节影响。

#### 面试官继续追问

- 为什么不直接把整份 PDF 放进 Prompt？
- 这个项目和普通知识库问答有什么区别？
- 你在原项目基础上具体做了什么？

#### 当前项目证据

当前项目已跑通 PDF 入库、Milvus 检索和千问回答，并增加了中文可视化前端与 Trace 展示。`main.py` 提供后端接口，`frontend/` 提供页面和本地代理。

#### 诚实边界

这是基于开源项目完成的学习与改造，不应把原作者的全部能力说成个人原创；当前也没有完整的生产评测、鉴权和高并发验证。

### 核心题 2：为什么使用 RAG，而不是直接让大模型回答？

#### 一句话回答

RAG 能把私有文档作为外部证据提供给模型，降低仅靠模型参数记忆造成的知识缺失和无依据回答。

#### 2～3 分钟回答

直接问模型时，它不知道刚上传的内部文档，也无法稳定给出来源。RAG 先检索相关片段，再把片段和问题一起交给模型，因此知识可以更新而无需重新训练模型，回答也更容易追溯。它并不能自动消除幻觉：如果解析丢内容、切分不合理或检索漏召回，模型仍可能答错，所以检索质量和引用同样重要。

#### 面试官继续追问

- RAG 和微调分别适合解决什么问题？
- 检索到了正确片段，为什么模型仍可能答错？
- 如何判断错误发生在检索阶段还是生成阶段？

#### 当前项目证据

项目会保存文档 Chunk 和向量，查询时返回支持文档并生成回答；Project Aurora 的事实问题能从已入库文档中得到负责人和上线日期。

#### 诚实边界

当前还没有系统化的 Recall@K、答案忠实度和引用正确率评测，因此只能说明链路可用，不能宣称 RAG 已经完全解决幻觉。

### 核心题 3：为什么浏览器不能直接调用大模型和向量数据库？

#### 一句话回答

浏览器是不可信客户端，直连会暴露 API Key、数据权限和内部存储接口。

#### 2～3 分钟回答

当前浏览器先访问本地代理，再由代理调用 FastAPI。代理负责文件校验、临时路径处理和错误映射；FastAPI 负责业务编排，并在服务端访问千问和 Milvus。这样可以把密钥和数据访问留在服务端，也便于统一鉴权、限流和审计。代价是增加一跳和一个需要维护的代理层，当前 Base64 上传还会带来体积膨胀。

#### 面试官继续追问

- 为什么文件上传不能只把浏览器本地路径传给后端？
- 代理层和 FastAPI 的职责怎样避免重复？
- 生产环境更适合 Base64、multipart 还是对象存储直传？

#### 当前项目证据

`frontend/server.py` 提供 `/api/ingest`、`/api/query` 和健康代理；`main.py` 提供实际业务接口，模型与向量库配置位于服务端。

#### 诚实边界

当前本地代理主要解决演示和协议适配问题，不等于已经具备完善的鉴权、限流、病毒扫描或对象存储方案。

### 核心题 4：项目中遇到过什么实际故障，你是怎么定位的？

#### 一句话回答

我遇到过 Milvus 因 Docker 内存不足无法正常写入，以及服务端离线后前端只看到请求失败的问题，都是通过分层检查定位的。

#### 2～3 分钟回答

排查 Milvus 时，我先确认容器状态和日志，发现 RocksDB 报内存分配失败，再检查 Docker/WSL 资源限制，调整内存后重新验证 Collection 写入。排查前后端时，我按浏览器、本地代理、FastAPI、Milvus和模型逐层检查，区分 HTTP 503、连接失败和真实无命中。这个过程让我发现当前部分向量库异常会被捕获成空结果，容易掩盖根因。

#### 面试官继续追问

- 为什么只检查端口不能证明 Milvus 可用？
- 为什么空结果不一定表示知识库没有答案？
- 生产环境应该怎样改进错误分类和监控？

#### 当前项目证据

实际日志出现过 `Cannot allocate memory`；调整 WSL/Docker 内存后完成真实写入。后端停掉时代理返回 503，Milvus 停掉时健康状态显示向量库不可用。

#### 诚实边界

这些是本地故障实验，尚未形成生产级监控、告警、自动重试和故障恢复体系。

### 核心题 5：这个项目目前最大的不足是什么，你会怎样继续优化？

#### 一句话回答

当前最大不足是缺少可量化的检索与回答评测，其次是错误分类、引用和流式体验不完整。

#### 2～3 分钟回答

我会先建立带标准证据片段的问题集，分别统计 Recall@K、答案正确率、引用正确率、延迟和 Token。随后增加混合检索或 Rerank，但必须用同一评测集验证收益。工程侧会区分连接失败、无 Collection、真实无命中和低相关命中，并把 Trace 升级为 SSE 流式事件。安全方面还需要鉴权、限流、敏感信息脱敏和租户数据隔离。

#### 面试官继续追问

- 为什么先做评测，而不是先加 Rerank？
- 如果只能先解决一个技术债，你选哪个？
- 流量扩大十倍后，架构上优先改什么？

#### 当前项目证据

现有前端已展示延迟、Token、路由和命中文档；学习记录也明确了空结果吞异常、非流式 Trace 和缺少评测等限制。

#### 诚实边界

混合检索、Rerank、SSE、鉴权和多租户均属于后续路线，当前不能写成已经实现的项目成果。
