## 3. P0：先解决“无法相信结果”的问题

### Q-01 没有检索与回答质量评测闭环

**现状与证据**

项目能跑通入库和查询，也记录延迟与 Token，但没有固定问题集和标准证据，无法系统计算 Recall@K、回答正确率、忠实度和引用正确率。

**影响**

- 无法证明 `1500/100` 切分参数是否合理。
- 无法比较 L2、Cosine、不同 Embedding 或 top-k。
- 无法证明 DeepSearch、ChainOfRAG 比 NaiveRAG 更好。
- 加入混合检索或 Rerank 后也无法验证收益。

**优化方案**

1. 从真实 PDF 整理 30～50 道问题，覆盖事实、同义表达、多跳和无答案场景。
2. 为每题标注标准来源、相关页或 Chunk、可接受答案要点。
3. 检索侧计算 Recall@K、Precision@K、MRR、空结果率和重复率。
4. 生成侧记录答案正确率、证据忠实度、引用正确率和拒答准确率。
5. 同时记录延迟、Token、模型调用数和失败类型。

**验收标准**

- 评测命令可重复运行并保存配置版本。
- NaiveRAG、DeepSearch、ChainOfRAG 能在同一数据集上对比。
- 任何优化 PR 都能展示质量、延迟和成本的前后变化。

**完成证据（2026-07-30）**

- 新增 `evaluation/datasets/milvus_v1.json`：固定 30 题、25 道可回答和
  5 道无答案问题，标注原始 PDF SHA-256、来源页、参考答案、答案要点和标签。
- 新增 `python -m evaluation.benchmark` / `deepsearcher-eval`：三类 Agent
  使用相同题集、Collection、top-k 和迭代配置，可分别运行检索或回答评测。
- 报告固定 `metric_version=1.0.0`，保存数据集/配置哈希、Git 状态、模型、
  参数、逐题结果和 JSON/CSV；来源重命名必须显式声明 alias 并写入报告。
- 检索指标覆盖 Recall@K、Precision@K、MRR、空结果率、重复率和无答案
  假阳性率；回答指标覆盖答案要点、证据要点、来源正确率和拒答准确率。
- 同时记录平均/P50/P95 延迟、Token、LLM 调用次数、错误率和安全失败类型。
- 真实基线与结论见
  `docs/开发记录/验证记录/2026-07-30-deepsearcher-evaluation-closure.md`。

### R-01 Milvus 异常可能伪装成空结果

**源码证据**

- `deepsearcher/vector_db/milvus.py` 的 `init_collection()` 和 `insert_data()` 捕获异常后只记录日志。
- `search_data()` 捕获异常后返回 `[]`。
- `list_collections()` 捕获异常后返回空集合信息。

**影响**

连接失败、Collection 不存在、维度不匹配和真实无命中可能在上层表现相似，用户可能得到“没有相关信息”，而不是明确系统错误。

**优化方案**

定义向量库异常类型：

```text
VectorDBUnavailable
CollectionNotFound
VectorDimensionMismatch
VectorInsertFailed
VectorSearchFailed
```

Milvus 适配层保留原始异常并转换为领域异常；FastAPI 再映射 HTTP 状态和稳定错误码。真正搜索成功但无命中时才返回空结果。

**验收标准**

- Milvus 离线时 API 返回依赖不可用，而不是成功空数组。
- 不存在 Collection、维度错误和真实无命中有不同错误码。
- Trace 记录失败阶段，但不泄露内部地址和敏感 metadata。

**完成记录（2026-07-30）**

- 新增向量库领域异常，Milvus 的初始化、写入、查询和列表失败不再被吞掉；只有真实查询成功但零命中时返回空列表。
- 核心 API 将依赖不可用映射为 `503/VECTOR_DB_UNAVAILABLE`，将 Collection 不存在和维度不匹配映射为 `409`，并只返回安全消息与可重试标记。
- 产品 API 保留稳定错误码，将安全失败消息持久化为 `failed` 助手消息；工作台明确区分系统故障、索引问题和无答案，并提供重试或返回知识库的操作。
- 服务端日志保留原始失败用于诊断，客户端响应不返回连接地址、内部异常和敏感 metadata。
- 已通过故障注入、接口、产品服务、React 交互、真实 Milvus 停机与恢复验收。详见 `docs/开发记录/验证记录/2026-07-30-deepsearcher-query-failure-visibility-verification.md`。

### R-02 RAGRouter 缺少索引范围校验

**源码证据**

`deepsearcher/agent/rag_router.py` 将模型输出转成索引后直接访问 `rag_agents[selected_agent_index]`。解析失败时会寻找最后一个数字，但没有检查：

```text
0 <= selected_agent_index < len(rag_agents)
```

**影响**

模型返回 0、9 或带有错误数字的解释文本时，可能选错 Agent 或抛出 `IndexError`。Python 负索引还可能静默选择末尾 Agent。

**优化方案**

- 使用结构化输出限制为候选枚举。
- 做整数和范围校验。
- 非法时 fallback 到可控 baseline，并记录路由失败。
- 建立带标准 Agent 标签的路由评测集。

**验收标准**

对空文本、无数字、0、负数、越界数字和带多个数字的输出均有确定行为和测试。

**完成记录（2026-07-30）**

- Agent 路由只接受完整匹配的单个正整数，并严格检查 `0 <= index < len(rag_agents)`；不再从解释文字中猜测最后一个数字。
- 空文本、解释、0、负数、越界和多数字输出统一回退到显式配置的 baseline Agent，路由 Token 仍被正确统计。
- 构造器拒绝空 Agent 列表、描述数量不一致和非法 fallback 索引。
- Trace 新增安全 `routing` 决策，记录最终索引、是否回退及稳定原因，不保存原始思维内容。

### R-03 CollectionRouter 缺少白名单过滤

**源码证据**

`deepsearcher/agent/collection_router.py` 解析模型返回的 Collection 名称后，与默认和无描述 Collection 合并，但没有把最终列表严格过滤到 `list_collections()` 的真实名称集合。

**影响**

模型生成不存在的 Collection 后可能触发 Milvus 异常，再被转换为空结果；多租户场景还存在越权访问风险。

**优化方案**

```text
模型输出
→ 类型检查
→ 真实 Collection allowlist
→ 当前租户权限过滤
→ 去重并保持稳定顺序
→ 无合法结果时使用明确 fallback
```

**验收标准**

- 不存在和未授权 Collection 永远不会进入搜索调用。
- Trace 能区分模型原始输出、过滤结果和 fallback 原因。

**完成记录（2026-07-30）**

- Collection 路由提示只暴露真实且允许访问的 Collection；模型结果随后再次与实时 `list_collections()` 和可选 `allowed_collections` 求交集。
- 模型幻觉名称、显式不存在名称和授权范围外名称会在搜索前被过滤；显式范围为空或全部非法时不会扩大到其他 Collection。
- 自动包含默认/无描述 Collection 和“无有效模型选择”回退采用稳定顺序，并明确记录 `fallback_used` 与原因。
- DeepSearch、ChainOfRAG、NaiveRAG 的模型路由、显式范围和关闭路由三条路径均复用同一 allowlist 逻辑。
- Trace 记录安全的 requested、selected、rejected、source 和 fallback reason；名称长度与格式受限，不记录原始提示词。

### R-04 LLM 结构化输出和索引校验不完整

**源码证据**

- DeepSearch 子查询与补充查询依赖模型输出可被 `literal_eval()` 解析的列表。
- ChainOfRAG 支持文档选择依赖 Python 索引列表。
- `_get_supported_docs()` 只检查 `int(i) < len(retrieved_results)`，没有拒绝负索引。

**影响**

格式异常可能中断请求；负数可能错误选择末尾文档；重复、空字符串和偏题查询也可能进入下一步。

**优化方案**

- 优先采用模型结构化输出或 JSON Schema。
- 校验列表类型、元素类型、长度、去重和非空文本。
- 文档索引严格检查 `0 <= index < len(results)`。
- 解析失败时执行可观察的 fallback，不静默猜测。

**验收标准**

为 Markdown 代码围栏、解释文字、空列表、负数、浮点数、越界和重复项增加测试。

**完成记录（2026-07-30）**

- 新增统一 `SelectionResult` 校验层，处理字符串列表、单值 Agent 枚举和零基文档索引。
- DeepSearch 初始子查询最多 4 条；解析失败或空列表回退到原问题。补充查询最多 3 条，并过滤空字符串、非字符串、重复项和已查询内容。
- ChainOfRAG 仅接受非布尔整数索引，严格检查 `0 <= index < len(results)`，去重并拒绝负数、浮点数和越界值；解析失败安全选择零篇文档。
- JSON/Markdown 代码围栏和仅含一个列表的解释文本可被解析，容器类型和元素语义仍需通过第二阶段校验。
- 过滤和回退会写入安全 Trace 或检索 metadata，格式错误不再中断整个问答请求。
- 自动化与真实查询结果见 `docs/开发记录/验证记录/2026-07-30-deepsearcher-routing-structured-output-verification.md`。

## 4. P1：可靠性、成本与数据治理

### D-01 Embedding 与 Collection 缺少版本绑定

**问题**

Collection Schema 记录维度，但不足以证明使用了哪个 Embedding 模型、版本、预处理和 metric。相同维度的不同模型也可能不兼容。

**优化方案**

为知识库保存：

```text
embedding_provider
embedding_model
embedding_version
dimension
normalization
metric_type
chunk_config_version
document_version
```

切换模型时新建版本化 Collection，完成重新向量化和回归评测后切流。

**验收标准**

查询前能校验模型与数据版本；迁移支持回滚；不会把新模型查询发送到旧语义空间。

**完成证据（2026-07-31）**

- 新增带双重 SHA-256 指纹的 Collection Manifest，绑定 Embedding provider、模型、版本、
  维度、归一化方式、metric、分块配置、文档版本和数据版本；缺字段、缺指纹或指纹不符均拒绝信任。
- Milvus 使用 Collection property、Qdrant 使用检索过滤掉的保留点、Oracle 使用 Collection
  description 持久化 Manifest；新建、追加和文档删除会同步推进数据版本。
- DeepSearch、ChainOfRAG 和 NaiveRAG 在生成查询向量和访问向量库之前校验所有选中
  Collection；相同维度但模型或版本不同也会明确拒绝。
- 旧 Collection 不按维度猜测兼容性，默认保护性阻止查询。用户工作台会显示“需重建”，
  禁用首页提问和历史回答重新生成，并提供完整资料一键重建入口。
- 重建先写入候选版本并读回校验 Manifest，成功后切换稳定别名；产品数据库保留上一物理版本，
  Milvus 真实测试验证了新旧模型切换和回滚。
- 实际使用升级前知识库完成“页面提示 → 一键重建 → 候选激活 → 页面变为已验证 →
  核心兼容性检查 → 真实问答”闭环。
- 详见 [D-01 Embedding/Collection 版本治理验证记录](../开发记录/验证记录/2026-07-31-deepsearcher-embedding-collection-manifest-verification.md)。

### D-02 `force_new_collection` 误删风险

**原始源码证据**

Milvus `init_collection()` 在 Collection 已存在且 `force_new_collection=True` 时直接调用 `drop_collection()`。

**优化方案**

- 生产配置禁止普通请求强制删除。
- 使用新 Collection、别名切换和延迟清理。
- 删除操作要求权限、二次确认、备份与审计。

**验收标准**

业务 API 无法误删生产 Collection；迁移失败可以切回旧版本。

**完成证据（2026-07-30）**

- Milvus、Qdrant、Oracle 驱动不再原地删除已存在 Collection；直接强制覆盖会返回明确的安全错误。
- 离线加载先完成路径检查、解析、切分和 Embedding，再写入候选版本；候选写入成功后才切换稳定别名。
- Milvus 首次切换会把原物理 Collection 改名为保留版本，并通过别名原子切到候选版本；支持切回保留版本。
- 整库删除只接受产品生成的 `kb_<32 位十六进制>` Collection，并要求 `X-Confirm-Collection` 与路径参数完全一致。
- 真实 Milvus 临时集合已完成“旧版写入 → 新版激活 → 新旧版本分别可检索 → 回滚 → 临时数据清理”验证。
- 详见 [D-02 安全集合重建验证记录](../开发记录/验证记录/2026-07-30-deepsearcher-safe-collection-rebuild-verification.md)。

### A-01 DeepSearch 的逐 Chunk LLM 过滤成本过高

**源码证据**

每个子查询会遍历 Collection 的每个候选 Chunk，并单独调用 LLM 返回 YES/NO。调用量近似随“子查询数 × Collection 数 × 候选数”增长。

**优化方案**

1. 向量召回后先跨查询去重。
2. 限制每个 Collection 的候选数。
3. 使用专用 Cross-Encoder/Reranker 或批量判断。
4. 简单问题路由到 NaiveRAG。
5. 加入模型调用、Token、总时间和并发预算。

**验收标准**

在固定评测集上，质量不下降的前提下显著减少模型调用数、P95 延迟和 Token。

**完成证据（2026-07-30）**

- 同一轮先合并不同子查询的向量候选，按排名交错去重；默认最多评估
  20 条候选，每批最多 10 条，不再逐 Chunk 调用模型。
- 批量模型只允许返回严格的零基索引数组；越界、负数、重复和错误类型会被
  过滤，解析失败显式回退到向量候选并记录 Trace，合法 `[]` 保持无结果。
- 仅当模型已经确认存在证据时，保留各子查询的首位向量候选作为覆盖保护；

### A-02 外层 asyncio 仍包含同步阻塞调用

**源码证据**

DeepSearch 使用 `asyncio.gather()` 调度多个子查询，但任务内部调用同步的 `llm.chat()`、`embed_query()` 和 `vector_db.search_data()`。

**影响**

代码形式上是 async，不代表真正非阻塞；同步网络调用可能阻塞事件循环，实际并发收益不确定。

**优化方案**

- 优先使用原生异步客户端。
- 暂时无法异步化的阻塞调用放入受限线程池。
- 使用 semaphore 控制外部调用并发。
- 增加单调用超时、总请求 deadline 和取消传播。

**验收标准**

用 1、2、4、8 个子查询比较总延迟和事件循环阻塞；并发量受控且超时可终止逻辑等待。

**完成证据（2026-07-30）**

- 同步 Collection 路由、Embedding、Milvus 搜索和批量 LLM 调用统一通过
  `asyncio.to_thread()` 移出事件循环，并由同一个 Semaphore 限制并发。
- 默认最大外部并发为 4、单操作逻辑超时 30 秒、单次检索总 deadline
  300 秒；三项均可通过 Agent 构造参数、查询参数和评测 CLI 覆盖。
- 每个并发子查询使用独立的 CollectionRouter 状态快照；结果与路由 Trace
  按输入子查询顺序合并，不受完成先后影响。
- 单操作超时、总 deadline、上游取消和 Provider 异常均向上传播，不再转成
  空结果；同步线程已开始执行后无法被 Python 强制终止，但其迟到结果会被丢弃，
  且在实际结束前持续占用并发槽位。
- 最终代码上的真实 OpenAIEmbedding + Milvus 探针：4 个查询从 `31018ms`
  降到 `7684ms`（`4.04×`），8 个查询从 `12330ms` 降到 `2187ms`
  （`5.64×`），事件循环最大心跳间隔为 `32ms`。1/2 查询没有稳定加速，
  原始结果完整保留，说明外部服务抖动明显。
- 三题 DeepSearch 质量指标全部保持，平均延迟为 `4878ms`，此前批量版同一
  抽样为 `16032ms`（该对比包含外部服务波动，真实 I/O 探针是主要并发证据）。
- 详细验证见
  `docs/开发记录/验证记录/2026-07-30-deepsearcher-async-retrieval-verification.md`。

### A-03 ChainOfRAG 中间答案错误传播

**问题**

下一轮追问依赖历史中间答案，早期错误事实可能改变后续查询方向。支持文档筛选本身也依赖 LLM。

**优化方案**

- 中间答案必须带支持引用。
- 没有支持文档的答案不进入可信上下文。
- 对关键事实做交叉检索。
- 检测重复追问和目标偏移。
- 将置信度和证据数量纳入停止条件。

**验收标准**

构造早期错误答案的测试，验证后续不会把无证据事实当成确定前提。

**完成证据（2026-07-30）**

- 第一轮固定检索原始问题，不再在零证据状态下让模型改写目标；后续追问只接收
  已验证且带 `[SxEy]` 引用的中间答案，以及不含答案内容的历史追问列表。
- 支持文档判定同时检查“完整支持中间答案”和“有助于主问题”；无支持文档、
  模型明确无结果、解析失败或目标偏移的答案只进入审计 metadata，不进入可信
  上下文、最终证据或下一轮提示。
- 追问经过空值、长度和规范化重复检查；重复追问在 Embedding 与向量检索前终止，
  Trace 记录 query guard、支持判定和 evidence stop gate。
- 产品运行时启用证据型 early stopping，默认至少需要 2 条不同证据；`confidence`
  是 `min(不同证据数 / 阈值, 1)` 的透明证据预算代理，不冒充概率置信度。
- 无召回文档时直接返回可验证的无结果中间状态，不再调用模型生成潜在幻觉。
- 固定 4 题、2 轮真实评测：Recall@5、MRR、来源准确率、拒答准确率均为
  `1.0000`，答案要点覆盖 `0.8333`，错误率和无答案误报率均为 `0`。
- 详细实现、失败基线和验证命令见
  `docs/开发记录/验证记录/2026-07-30-chain-of-rag-evidence-verification.md`。

### S-01 全局配置不适合并发和多租户

**问题**

`init_config()` 创建并替换模块级 LLM、Embedding、VectorDB 和 Agent 对象。单用户本地调用简单，但并发切换时可能出现新旧对象并存，多 worker 状态也不同；无法天然隔离租户配置和 Collection 权限。

**优化方案**

- 应用生命周期创建共享客户端。
- 通过依赖注入传入请求服务。
- 租户身份、模型策略和 Collection 权限进入请求上下文。
- 配置采用版本化发布，旧请求自然结束后回收旧实例。

**验收标准**

两个并发租户使用不同模型和 Collection 时互不影响；多 worker 配置一致且可回滚。

**完成结果（2026-07-31）**

- FastAPI 不再从模块级 globals 取运行时组件；lifespan 创建 `RuntimeRegistry`，业务路由通过
  `Depends(get_runtime)` 获得请求租约，查询、入库、Manifest、重建和删除共用同一授权上下文。
- `RuntimeControlStore` 用共享 SQLite 持久化配置版本与租户绑定；worker 每次请求读取活动版本，
  仅在本进程按需构建并缓存 runtime。发布使用期望版本做 CAS，失败候选不会生效。
- runtime 采用引用计数回收：新版本发布后旧请求继续使用原 LLM/Embedding/VectorDB/Agent，
  最后一个旧租约结束且版本不再被任何租户使用时才关闭向量客户端。
- 租户身份由 `X-DeepSearcher-Tenant` 与服务令牌共同解析；模型策略、版本号、绑定 revision 和
  Collection 白名单进入 `RuntimeRequestContext`。调用方指定 Collection 不能扩大服务端权限。
- 租户管理接口支持版本发布与回滚；模型配置、`model_policy` 和 Collection 白名单作为一个
  原子版本一起切换。新租户首版本没有公共基线回滚入口，避免回滚成默认租户的 `*` 权限。
- 热更新中的密钥禁止明文写入控制库，只允许 `{"$env": "ENV_NAME"}` 引用 API 进程环境变量；
  产品服务的查询、入库、重建和删除请求统一携带受信租户头。
- 单元/API 验证覆盖旧请求延迟回收、两个并发租户使用不同模型与 Collection、越权 403、发布

- 2026-08-01 补充收口共享 Agent 的实例状态：Collection 路由、Agent 路由、ChainOfRAG

### S-02 Trace 非流式且需完善敏感信息治理

**现状**

项目已经有结构化 `TraceCollector` 和前端展示，但主要在请求结束后返回完整结果。

**风险**

- 长查询期间用户看不到实时进度。
- 完整问题、文档、reference 和 metadata 可能包含敏感信息。
- Trace 不能被误称为模型思维链。

**优化方案**

使用 SSE 发送受控阶段事件：开始、路由、检索计数、支持文档、反思、完成和错误。对路径、metadata、文档内容做字段级脱敏，设置保存期限和访问权限。

**验收标准**

前端可增量展示事件；断连能停止或回收任务；敏感字段不会出现在客户端和日志中。

**完成结果（2026-08-01）**

- 核心 API 新增 `POST /query/stream`，以版本化 SSE 发送 `started`、`routing`、
  `iteration`、`retrieval`、`support`、`reflection`、`completed`、`error` 和
  `cancelled`。事件包含请求 ID 与严格递增序号，不通过日志文本反向解析进度。
- `TraceCollector` 升级为 v3：不再保留或返回原问题、子查询、Collection 名和中间答案；
  只返回最终受支持的证据，最多 5 条、每条 600 字，并对凭据、邮箱、本地路径、URL 查询
  参数和自由文本 metadata 做白名单/脱敏处理。Agent 日志只保留阶段、数量和 Token 统计。
- 浏览器通过产品 BFF 的 POST 流式接口消费事件。BFF 再次按字段白名单重建阶段事件，
  `completed` 只返回已落库的 Message/Citation，不把核心 Trace 或调试字段交给普通用户。
  阶段事件不持久化，响应设置 `no-store`、`no-transform` 和 `X-Trace-Retention: transient`。
- React 对话页增量展示检索阶段、证据数量与充分性检查，明确标注“系统执行阶段，不是模型
  的思维链”；支持“停止生成”，长对话会自动滚到完整可见且不被输入框遮挡的进度卡片。
- 断连采用协作取消：浏览器 AbortController 关闭 BFF 上游流，核心线程在显式阶段边界检查
  cancellation event；任务退出后释放 runtime lease。应用停机还会等待未完成的清理任务。
- 自动化覆盖安全事件顺序、字段剔除、错误映射、浏览器分片解析、停止状态落库和真实
  Uvicorn 客户端断线。真实 Milvus/模型验证首事件为 1.597 秒，随后按路由、检索、支持、
  反思、完成递增到达；浏览器验证为 0 warning / 0 error。
- S-03 已随后移除 GET 查询路由；旧学习控制台和产品 BFF 均通过 POST Body 调用核心查询，
  原问题不再由项目代码写入查询 URL。阶段事件与 Agent 日志也不包含原问题或内部内容。
- 2026-08-01 补充收口：BFF 现在强制校验事件版本、事件名、同一请求 ID 和连续序号，并限制
  单行、单事件和数据行数量；非法上游流统一映射为 `502/QUERY_STREAM_INVALID`。引用落库再次
  执行字段类型、长度、数值范围、URL 与数量白名单，且只能在当前对话知识库中关联文档，阻断
  跨知识库 `document_id`/SHA 绑定。
- Trace 的 HTTP(S) reference 统一经过公网 URL 规范化，拒绝凭据 URL、IP、内网主机、非标准
  端口和非 HTTP(S) 协议，并同时删除 query 与 fragment。

### S-03 API 错误协议不稳定且可能泄漏密钥和内部信息

**源码证据**

- `main.py` 的四个业务接口都用宽泛的 `except Exception` 把业务异常统一包装成 500，并把 `str(e)` 放入 `detail`。
- `/set-provider-config/` 成功响应原样返回 `request.config`，该字典允许包含 `api_key` 等敏感配置。
- 当前接口没有认证与授权，文件路径、配置切换和查询能力没有访问边界。
- 查询使用 GET，原始问题会进入 URL 和常见访问日志；CORS 仅在直接运行脚本时启用，且允许范围过宽。

**影响**

- 客户端无法区分请求错误、文件不存在、上游限流、依赖不可用、超时和服务 Bug，难以制定可靠重试策略。
- 原始异常可能泄漏绝对路径、连接信息或供应商响应。
- 配置响应可能把密钥带到浏览器状态、代理日志和监控系统。

**优化方案**

- 建立领域异常：参数、资源不存在、冲突、限流、依赖不可用、超时和内部错误。
- 返回稳定 `code`、安全 `message` 和 `request_id`，完整堆栈只写入脱敏服务端日志。
- 配置输出使用只读 DTO，密钥永不回显；日志对路径、Token 和文档内容做字段级脱敏。
- 为配置、入库和查询接口增加认证、角色权限、Collection 授权和审计。
- 敏感或较长查询改用 POST Body；CORS 由统一配置加载并只允许可信 origin。

**验收标准**

API 测试覆盖 400/404/409/422/429/503/504/500；响应和日志扫描不出现测试密钥与敏感绝对路径；未授权请求不能切换配置或读取任意服务端文件。

**完成结果（2026-08-01）**

- 核心同步查询改为 `POST /query` JSON Body，GET `/query/` 不再注册；产品主链路和保留的
  `/console` BFF 均已迁移，不再由项目把用户问题放入 URL 或常规访问日志。
- 核心与工作台 BFF 统一错误信封：稳定 `code`、安全 `message`、`request_id` 和
  `retryable`，并在响应头返回同一 `X-Request-ID`。Pydantic 422、未知路由 404、限流 429、
  依赖 503、超时 504 和未知故障 500 都不会返回原始异常、请求体或本机路径。
- 向量库、运行时和 API 领域错误分别映射 400/401/403/409/422/429/502/503/504/500；
  未知异常日志只记录请求 ID、方法、路由模板和异常类型，不记录异常文本。Provider 更新只返回
  provider、租户和运行时版本，配置及密钥永不回显。
- 默认查询入口增加每进程固定窗口准入限制（60 次/60 秒，可配置，0 仅用于隔离开发）；429
  返回 `Retry-After`。这是单机保护层，不冒充多 worker 的分布式配额系统。
- CORS 默认关闭，只接受 `DEEPSEARCHER_CORS_ORIGINS` 中精确列出的 HTTP(S) origin；通配符、
  凭据型 origin、带路径/查询/fragment 的值会被忽略。允许的方法和请求头也采用显式白名单。
- 文件入库、网站入库、Provider 切换、Manifest、重建、删除、查询和 runtime 上下文都要求
  有效服务令牌；未配置服务令牌时受保护入口直接拒绝。`start.ps1` 为核心 API 与工作台生成同一枚不落盘临时服务令牌，
  管理端使用另一枚令牌，普通浏览器用户不接触这些凭据。
- 自动化覆盖验收要求的 400/404/409/422/429/503/504/500，以及 401 未授权配置/文件读取、
  请求 ID 透传、可信/不可信 CORS、响应与日志密钥/绝对路径扫描、核心 SSE 请求 ID 对齐、
  未知 `/api` 不再错误回退到 SPA。全量结果为 646 passed、9 skipped。
- 2026-08-01 补充审计覆盖向量库、Loader/Crawler、Embedding、LLM、runtime 与工作台适配层；

### O-01 健康检查语义不够强

**问题**

端口可连接不等于服务已就绪；模型配置存在也不等于模型调用成功。当前本地实验已观察到 Milvus 端口状态和真实客户端可用性可能不一致。

**优化方案**

区分：

- liveness：进程是否活着。
- readiness：依赖是否能完成最小真实操作。
- degraded：部分能力不可用但服务仍可响应。

**验收标准**

Milvus 未就绪、模型鉴权失败和后端离线能返回不同健康状态。

**完成记录（2026-08-01）**

- 核心 API 拆分 `GET /health/live`、`GET /health/ready` 和受服务令牌保护的 `POST /health/diagnostics`；旧 `GET /health` 保留为 readiness 兼容入口。
- readiness 执行最小 Milvus RPC，不再把端口连通或 Python 对象已创建当成就绪；运行时或向量库失败返回 `503/not_ready`。
- 深度诊断真实调用 LLM 与 Embedding；模型鉴权失败返回 `200/degraded` 和组件级 `PROVIDER_AUTH_FAILED`，默认缓存 300 秒，普通健康刷新不触发付费调用。
- 用户工作台直接聚合核心健康契约，不再独立探测 Milvus TCP 端口；工作台另有独立 liveness，控制台提供显式“深度检查”。
- `start.ps1` 用 liveness 等待进程启动，`status.ps1` 用 readiness 判断完整服务状态。
- 真实故障注入已验证三种不同结果：Milvus 停机为 `milvus=DEPENDENCY_UNAVAILABLE`，核心离线为 `fastapi=BACKEND_OFFLINE`，无效模型密钥为 `degraded/PROVIDER_AUTH_FAILED`；故障后服务均已恢复。
- 2026-08-02 补充收口深度探针的返回值语义：LLM 必须返回非空内容，Embedding 必须返回
  非空、有限数值且与声明维度一致的向量；“调用未报错但结果不可用”统一标记为
  `DEPENDENCY_INVALID_RESPONSE`，不再误报 ready。
- 工作台只接受版本、服务名、模式、HTTP 状态、请求 ID、组件状态和错误码均符合契约的核心
  健康响应；错状态码或错请求 ID 会降为 `BACKEND_INVALID_HEALTH_RESPONSE`。
- `status.ps1` 解析 JSON 健康状态并只把精确 `ready` 当作就绪，`200/degraded` 不再被误判为
  全部 ready。Worker 同时校验心跳和受控进程元数据；PID 校验不再依赖可能无界卡住的 WMI/CIM，
  并兼容 Windows PowerShell 5.1 与 PowerShell 7 的 UTC 解析差异。
- 自动化、构建、浏览器和故障注入证据见
  `docs/开发记录/验证记录/2026-08-01-deepsearcher-health-semantics-verification.md` 和
  `docs/开发记录/验证记录/2026-08-02-deepsearcher-health-contract-hardening-verification.md`。

### O-02 `score` 与 distance 语义混淆

**源码证据**

Milvus 搜索结果把 `b["distance"]` 写入 `RetrievalResult.score`。当前 L2 越小越近，但 `score` 容易让调用方误以为越大越好。

**优化方案**

- 结果结构显式保存 `metric_type` 与 `distance`。
- 如果需要统一相似度，定义并测试清楚转换公式。
- 前端根据 metric 展示“距离”或“相似度”，不要统一写“分数”。

**完成记录（2026-08-01）**

- `RetrievalResult` 显式区分 `distance`、`similarity` 和 `rank_score`，同时保存
  `metric_type`、`score_kind` 与 `higher_is_better`；旧位置参数 `score` 仅作为迁移兼容入口，
  不再进入 Trace 的公开契约。
- Milvus 根据实际 metric 映射 L2/IP/COSINE，混合检索 RRF 使用排序分；Qdrant 读取 Collection

- Trace 升级为 v3，序列化明确的指标字段；前端分别显示“距离 · 越小越近”、“相似度 · 越大越近”

### O-05 文件上传与临时路径治理

**现状**

当前产品工作台已经使用 multipart，保存 Document/IngestJob、SHA-256 和持久文件，并由 BackgroundTasks 调用 DeepSearcher；旧 `/console` 仍通过 Base64 和临时目录适配原 `/load-files/`。产品链路消除了 Base64 膨胀并提供了可恢复的业务状态，但上传路由仍完整读取文件到内存，任务仍依赖 Web 进程，持久文件也缺少删除、配额、扫描和长期生命周期治理。

**优化方案**

- 保留当前小文件 multipart，并改为流式大小限制。
- 大文件采用对象存储直传、持久任务 ID 和独立 Worker。
- 限制类型、大小、页数和解析时间。
- 对持久文件增加随机名称、受控目录、最小权限、配额和删除策略。
- 为 queued/processing 任务增加租约、重试、死信和进程恢复。
- Trace 与错误响应不返回绝对路径。

**本地小文件闭环完成记录（2026-08-01）**

- 产品工作台和旧控制台均改为 multipart 分块上传；服务端每次最多读取 1 MiB，不再读取整份文件或编码 Base64。
- 上传过程中执行单文件大小限制与 SHA-256，随后由限时独立进程验证 PDF 结构和页数；异常、超时、空文件和加密/损坏文件返回稳定安全错误码。
- 持久文件使用 48 位随机十六进制名称、受控知识库目录、最小可用权限和原子移动；默认限制 20 MiB/文件、500 页、200 份/知识库、512 MiB/知识库、2 GiB/实例。
- 新增独立 `frontend.product.worker`；一键启动、停止和状态脚本均管理该进程，工作台健康检查展示 Worker 状态。
- IngestJob 持久化可执行时间、租约所有者、租约过期时间、重试计数、最大重试数和安全错误；支持过期租约恢复、指数退避、安全自动重试和死信。
- 核心入库接口支持 `replace_document_id`，重试前按 SHA-256 清理同一文档旧分块，防止重复引用；完成状态不确定的读取超时不自动并发重试。
- 保留手动重试、文档/知识库删除闭环；启动时额外清理过期 `.part` 和超过保护期的无记录孤儿 PDF。
- 新增 `GET /api/ingest-jobs/{job_id}`，上传响应中的持久任务 ID 可独立查询。
- 自动化回归、真实浏览器上传和数据库/文件/Milvus 删除核对均已通过；详见
  `docs/开发记录/验证记录/2026-08-01-deepsearcher-upload-lifecycle-verification.md`。

当前产品明确拒绝超过 20 MiB 的大文件，因此尚未引入对象存储和浏览器直传；如果后续产品范围需要支持大文件，再单独完成 O-05B 对象存储、多段上传、病毒扫描和配额计费，不复用本地小文件路径冒充大文件能力。

### O-06 混合检索路径已有实现但缺少评测

**原问题**

Milvus 适配层在 `hybrid=True` 时会创建 BM25 稀疏向量字段，并使用 dense + BM25 与 `RRFRanker()` 执行混合搜索。

**问题**

有实现不等于有效。当前缺少与纯向量检索在同一问题集上的 Recall@K、精确率、延迟和资源对比。

**优化方案**

使用包含专有名词、编号、日期和同义表达的问题集，比较 dense、BM25 和 hybrid；记录 RRF 参数和索引版本。

**验收标准**

只有在质量收益足以覆盖额外索引、存储和延迟后，才将 hybrid 作为默认策略。

**完成记录（2026-08-01）**

- Milvus 新增显式 `dense`、`bm25`、`hybrid` 检索模式；旧 `auto` 行为保持兼容，Dense 查询显式
  指定 `embedding` 字段，BM25 查询显式指定 `sparse_vector`。
- RRF 从依赖 SDK 隐式默认值改为可配置并记录的 `rrf_k`，默认 60；返回值继续使用
  `metric_type=RRF/BM25` 和 `rank_score`，不与距离混用。
- 新增 `python -m evaluation.retrieval_compare`：只允许操作 `eval_` Collection，固定数据集和
  源文件哈希，同一查询只生成一次 Embedding，三种模式重复 3 次并轮换顺序。
- 报告保存逐题/分标签 Recall@K、Precision@K、MRR、证据覆盖、空结果、错误率、Embedding 与
  检索 P50/P95、排序稳定率、Manifest、RRF 参数、字段和索引资源结构。
- 真实 30 题、25 道可回答题结果：Dense Recall@5 `1.0000`、MRR `0.9400`、证据要点覆盖
  `0.9169`；Hybrid 分别为 `1.0000`、`0.8733`、`0.9169`，综合质量下降 `0.022233`；BM25
  Recall@5 为 `0.6800`。三种模式均 0 错误、排序稳定率 100%。
- Hybrid 需要在相同 16 行上额外维护稀疏向量字段和 `SPARSE_INVERTED_INDEX`；没有获得质量收益，
  因而 `deepsearcher/config.yaml` 明确保持 `hybrid: false`。
- 临时评测 Collection、版本和别名均已删除。完整结果见
  `evaluation/results/2026-08-01-o06-dense-bm25-hybrid-v1/report.json`，验证过程见
  `docs/开发记录/验证记录/2026-08-01-deepsearcher-hybrid-retrieval-evaluation.md`。

### O-07 FastAPI 导入即初始化外部组件，API 测试与真实依赖耦合

**原问题**

`main.py` 曾在模块导入阶段立即创建 `Configuration` 并调用 `init_config()`，导致导入、测试与真实 LLM、Embedding、Crawler 和 Milvus 初始化状态绑定。

**完成记录（2026-07-30）**

- 新增 `create_app()` 应用工厂；模块导入只注册路由，不创建外部客户端。
- FastAPI lifespan 创建并持有不可变运行时快照，退出时关闭应用拥有的 Milvus 客户端。

## 6. 推荐优化顺序

### 第一阶段：让结果可测、失败可见

1. 建立最小评测集和基线。
2. 修复 Milvus 异常吞掉问题。（已完成）
3. 完善 RAGRouter、CollectionRouter 和结构化输出校验。（已完成）
4. 区分系统错误、真实无命中和低相关结果。（已完成系统错误与真实无命中区分）

### 第二阶段：降低 Agent 成本与错误传播

1. 为 DeepSearch 增加调用、Token、时间和并发预算。
2. 用批量或专用 Reranker 替代逐 Chunk LLM 调用。
3. 修复 ChainOfRAG 负索引和重复 Embedding。（已完成）
4. 为中间答案增加支持证据与重复追问检测。（已完成）

### 第三阶段：完善数据和用户体验

1. 建立 Embedding/Collection 版本治理与安全迁移。（已完成）
2. 增加页码或章节级引用。
3. 将 Trace 升级为脱敏 SSE。
4. 补充鉴权、限流、缓存和多租户隔离。
5. 评测混合检索，决定是否默认启用。
