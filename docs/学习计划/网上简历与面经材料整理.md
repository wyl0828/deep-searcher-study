### 2.1 案例 A：代码风险识别 Agent 与知识图谱

#### 背景

- 岗位：汽车软件/算法研发组 Agent 开发实习。
- 目标：识别跨模块代码变更风险，提高代码评审效率，并向端到端测试提供风险信息。
- 架构关键词：Google ADK、A2A、多 Agent、知识图谱、FastAPI、D3.js。

#### 主要工作

- 设计“中控 Agent + 意图识别 Agent + 垂直场景 Agent”的分层协作架构。
- 开发跨模块调用风险识别 Agent，分析代码变更影响并生成标准化风险报告。
- 从代码提交、仓库、模块、文件、类等信息中抽取节点和关系，构建代码域知识图谱。
- 使用配置化流水线完成多仓库图谱自动构建。
- 通过 FastAPI 暴露知识图谱查询服务，提供节点上下游依赖等查询能力。
- 使用 D3.js 实现图谱可视化。

#### 简历中的量化表达

- 跨模块风险召回率：53% → 74%。
- 单 commit 识别平均耗时：42% 降低。
- 风险分析场景 Token 消耗：37% 降低。

> 这些指标需要能解释测试集、基线、计算方法和样本量，否则容易成为追问风险点。

## 三、可复用的简历写法

### 3.1 项目描述公式

推荐顺序：

> 业务场景 → 核心链路 → 技术难点 → 个人职责 → 方案 → 可验证结果

示例：

> 面向在线面试场景，负责 AI 评分与追问链路。针对长耗时调用和节点强依赖问题，将流程拆分为可恢复状态节点，并增加幂等、超时和补偿机制，降低重复评分与状态错乱风险。

### 3.2 比较有效的表达特征

- 不只罗列技术栈，而是解释技术解决了什么问题。
- 能说清“为什么不用更简单的方案”。
- 指标包含基线、结果和统计口径。
- 明确个人负责的模块，避免把团队成果全部写成个人成果。
- 项目亮点与岗位匹配：Agent 岗强调评测、工具调用和可观测性；Java 岗强调并发、缓存、数据库和可靠性。

### 3.3 高风险表达

- “熟悉”技术过多，但项目中没有使用证据。
- 每个优化都有整齐的大幅提升，却说不出测试方法。
- 堆叠 Singleflight、Fencing Token、Outbox 等术语，却无法解释适用条件。
- 把“使用 AI 编程工具”本身当作核心能力。
- 项目复杂度明显超出时间、团队或实习生权限。

## 六、截图中参考答案的有效内容

### 6.1 ReAct 与 Plan-Execute-Replan

- ReAct：推理和行动交替，每轮根据当前观察决定下一步，适合不确定性高、需要边执行边探索的任务。
- Plan-Execute-Replan：先规划多个步骤，再执行；遇到偏差时重新规划，适合结构较清晰的多步骤任务。
- 主要取舍：ReAct 灵活但模型调用和 Token 开销通常更高；Plan-Execute-Replan 批量执行效率更高，但初始计划错误会带来返工。

### 6.2 降低 Agent Token 消耗

- 精简系统提示词和工具描述。
- 对稳定提示词使用 Prompt Cache。
- 使用滑动窗口、摘要和检索式记忆控制上下文。
- 清理重复消息和无关工具输出。
- 简单任务路由到小模型。
- 对结构化任务使用确定性流程，减少模型反复推理。
- 限制最大轮数、最大输出和工具返回大小。
- 对语义相同请求或检索结果使用缓存。

### 6.3 Function Calling、MCP、Skill、Rule

- Function Calling：模型以结构化参数表达“调用哪个函数”，由应用实际执行。
- MCP：客户端与外部工具/资源/提示模板之间的标准化交互协议。
- Skill：围绕某类任务封装的能力说明、流程、工具和资源。
- Rule：约束 Agent 的行为边界和执行规范。

它们可以组合使用，并不是互相替代关系。

### 6.4 Temperature 与 Top-K

- Temperature：缩放 logits，影响概率分布的平坦程度；通常越低越确定，越高越发散。
- Top-K：只保留当前概率最高的 K 个候选 Token，再从候选中采样。
- 工程选择不能只记“低温小 K 做代码、高温大 K 做创作”，还要结合模型、Top-P、任务容错率和评测结果。

### 6.5 Redis Hash 大 Key

- 先通过监控和扫描定位大 Key。
- 按用户、时间或一致性哈希等维度分片。
- 使用渐进迁移：旧结构与新结构双写，优先读新结构，未命中回源旧结构。
- 给旧缓存设置合理过期时间，并观察命中率、错误率和容量。
- 大量字段删除使用 HSCAN + 分批 HDEL，避免一次性操作阻塞。

### 6.6 ThreadLocal 风险

- 线程池会长期复用线程，忘记清理时容易把上次请求的数据带到下次请求。
- `ThreadLocalMap` 的 Key 是弱引用，但 Value 仍可能被 Entry 强引用。
- 应在 `try/finally` 中调用 `remove()`。
- 异步切换线程后，普通 ThreadLocal 不会自动传播。
- 对请求身份、链路信息等上下文，优先考虑显式传参或受控的上下文传播机制。

### 6.7 ACID

- 原子性：事务内操作全部成功或全部回滚。
- 一致性：事务前后满足数据库约束和业务不变量。
- 隔离性：并发事务的互相影响受隔离级别控制。
- 持久性：提交后的结果在故障恢复后仍可保留。

### 6.8 创建 Java 对象

一般可从以下过程回答：

1. 检查目标类是否已经完成加载、链接和初始化。
2. 在堆中分配对象内存，常见方式包括 TLAB、指针碰撞或空闲列表。
3. 将实例字段初始化为零值。
4. 设置对象头。
5. 执行实例初始化逻辑和构造方法。

## 七、需纠正或谨慎使用的内容

### 7.1 技术表述不严谨

1. **“TCP 保证数据包一定到达”不准确。**  
   TCP 提供可靠、有序的字节流，会确认、重传和去重，但在网络中断或连接失败时仍可能无法交付，应用必须处理超时和失败。

2. **“Redis Key 过期后立即删除”不准确。**  
   Redis 主要结合惰性删除和定期删除，因此过期 Key 可能短时间仍占内存。

3. **“ThreadLocal 的 Key 被回收后 Value 永远无法回收”过度简化。**  
   线程访问 ThreadLocalMap 时可能清理陈旧 Entry，线程结束后也可回收；长生命周期线程加上不再访问才更危险。

4. **“每次 new 都会类加载”不准确。**  
   只有类尚未完成相应加载/初始化时才触发，已加载的类不会为每个对象重复加载。

5. **“对象都在堆上”不够严谨。**  
   Java 语义上通常这样理解，但 JIT 可能通过逃逸分析进行标量替换或消除分配。

6. **“隔离性就是两个事务互不可见”不准确。**  
   可见性取决于隔离级别；读已提交、可重复读和串行化的行为不同。

7. **undo/redo log 的描述过于流程化。**  
   undo log 主要支持回滚和 MVCC，redo log 保障 InnoDB 崩溃恢复；不能简单理解成每次更新分别只写一种日志。

8. **Query Rewrite 不等同于 Agentic RAG。**  
   单次固定改写属于检索流水线优化；只有系统能根据状态和反馈自主选择检索策略、循环并决定停止时，才更接近 Agentic。

### 7.2 指标口径可疑

以下数字只能当作“简历表达示例”，不能直接使用：

- “用户意图识别率提高 140%”。
- “top 级问题实现 99% 人力释放”。
- “数据库压力降低 90%”。
- “查询速度提高 200%”。
- “客户满意度提升 25%”。
- “单 commit 识别平均耗时降低 42%”。

使用前至少补齐：

- 优化前后的绝对值。
- 数据集或请求规模。
- 统计时间范围。
- 测试环境。
- 计算公式。
- 是否由本人独立负责。

### 7.3 简历真实性风险

- 网上简历中的公司、项目、指标不能移植成个人经历。
- 没有真实做过的技术不要写“熟悉”，更不要写源码级掌握。
- 一个项目放入过多高级方案会引发连续追问。
- 最好选择 2～3 个真正能运行、能演示、能解释权衡的核心亮点。

## 八、与当前 DeepSearcher 项目的可结合方向

这批材料与当前项目最相关的是：

1. RAG 检索评测：Recall@K、Precision@K、Rerank、混合检索、动态 Top-K。
2. Agent 流程：ReAct、Plan-Execute-Replan、失败重试、停止条件。
3. 运行可观测性：节点耗时、Token、工具调用、检索来源和异常。
4. 上下文管理：会话窗口、摘要、检索式记忆和污染控制。
5. 稳定性：超时、重试、幂等、降级和人工兜底。
6. 成本优化：模型路由、缓存、结构化输出和工具返回裁剪。
