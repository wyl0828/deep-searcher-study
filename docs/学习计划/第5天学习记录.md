30 秒人话版：

> Milvus 在项目里负责保存文档片段的向量，并根据用户问题向量找最接近的片段。可以把一个 Collection 理解成一张“向量知识表”：每行有向量、文本、来源和附加信息。入库时系统把每个文档片段写进去；查询时用同维度的问题向量做近邻搜索。当前默认用 L2 距离，所以返回值更准确地说是 distance，越小越接近。这个环节的风险是：维度不一致会直接失败，连接失败也可能被上层误看成“没搜到结果”。

## 1. 今天先记住一条链路

```text
当前向量模型的维度：比如 1024
  （代码名：embedding_model.dimension）
  ↓ 用这个维度创建向量知识表
  （代码名：Milvus.init_collection(dim=...)）
向量字段固定为同样维度
  （代码名：embedding FLOAT_VECTOR(dim=...)）
  ↓ 指定怎么计算“远近”
  （代码名：metric_type="L2"）
建立向量检索规则/索引
  （代码名：index_params）
  ↓ 写入文档片段的向量、文本、来源
  （代码名：insert_data(chunks)）
  ↓ 用用户问题的向量查最接近的片段
  （代码名：search_data(query_vector)）
返回命中的文档片段和距离值
  （代码名：RetrievalResult(text, reference, metadata, distance)）
```

先按中文理解：向量库先规定“每条向量多长、怎么比远近”，再负责写入和检索。括号里的英文只用于追源码。

面试时可以这样说：

> Milvus Collection 可以理解为一张带向量字段的表。DeepSearcher 创建 Collection 时会固定 `embedding` 字段的维度，插入时写入 Chunk 的向量、文本、来源和 metadata；查询时用同维度的 query vector 在 `embedding` 字段上做近邻搜索，返回文本、来源、metadata 和距离值。

## 3. Milvus Collection 是什么

在本项目里，一个 Milvus Collection 保存一批可检索知识片段。它不是只存向量，还同时存文本和引用信息。

当前默认 schema：

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `id` | `INT64` | 主键，`auto_id=True` 自动生成 |
| `embedding` | `FLOAT_VECTOR(dim=...)` | 向量字段，用于近邻检索 |
| `text` | `VARCHAR` | Chunk 文本 |
| `reference` | `VARCHAR` | 来源文件或 URL |
| `metadata` | `JSON` | 扩展信息，例如 `wider_text` |

源码证据：

```python
schema = self.client.create_schema(
    enable_dynamic_field=False,
    auto_id=True,
    description=description,
)
schema.add_field("id", DataType.INT64, is_primary=True)
schema.add_field("embedding", DataType.FLOAT_VECTOR, dim=dim)
schema.add_field("text", DataType.VARCHAR, max_length=text_max_length)
schema.add_field("reference", DataType.VARCHAR, max_length=reference_max_length)
schema.add_field("metadata", DataType.JSON)
```

这里 `enable_dynamic_field=False` 表示不允许随便塞 schema 外字段，优点是结构明确，代价是扩展字段要么放进 `metadata`，要么改 schema。

## 4. 索引和 metric 管什么

源码中默认：

```python
metric_type: str = "L2"
index_params = self.client.prepare_index_params()
index_params.add_index(field_name="embedding", metric_type=metric_type)
```

可以把它拆成两层：

- `embedding` 字段：存什么向量。
- `metric_type="L2"`：用什么距离规则比较向量。

当前项目默认是 L2 距离。面试表达要谨慎：

> L2 是距离，不是“越大越相似”的分数。值越小，通常表示越接近。

本次真实实验中，Milvus 返回的 L2 distance 是平方距离：

```text
query = [0.9, 0.0]
doc   = [1.0, 0.0]
平方 L2 = (0.9 - 1.0)^2 + (0 - 0)^2 = 0.01
```

所以看到 `distance=0.01` 是合理的。

## 5. 插入数据时发生什么

如果要追代码，可以看：`Milvus.insert_data()`

插入时项目从每个 Chunk 中取四类信息：

```python
texts = [chunk.text for chunk in chunks]
references = [chunk.reference for chunk in chunks]
metadatas = [chunk.metadata for chunk in chunks]
embeddings = [chunk.embedding for chunk in chunks]
```

再组装为 Milvus 行数据：

```python
{
    "embedding": embedding,
    "text": text,
    "reference": reference,
    "metadata": metadata,
}
```

注意：

- `id` 不需要手动传，因为 Collection 是 `auto_id=True`。
- 如果 `chunk.embedding` 是 `None` 或维度不对，插入会失败。
- 当前实现捕获异常后写 critical 日志，但不会把异常重新抛给上层；这是一个可靠性短板。

## 6. 检索数据时发生什么

如果要追代码，可以看：`Milvus.search_data()`

默认非 hybrid 搜索调用：

```python
self.client.search(
    collection_name=collection,
    data=[vector],
    limit=top_k,
    output_fields=["embedding", "text", "reference", "metadata"],
    timeout=10,
)
```

然后把 Milvus 返回结果转换为项目统一对象：

```python
RetrievalResult(
    embedding=b["entity"]["embedding"],
    text=b["entity"]["text"],
    reference=b["entity"]["reference"],
    score=b["distance"],
    metadata=b["entity"]["metadata"],
)
```

这里 `score` 字段名有一点迷惑：如果 metric 是 L2，它实际是 distance。面试时要主动解释：

> 项目统一对象叫 `score`，但 Milvus 这里填的是 `distance`。所以解释排序时必须看 metric。


```text

```

### 7.2 创建临时 Collection

本次实验创建临时 Collection：

```text
day5_milvus_l2_demo
```

字段：

```text
id         INT64 auto_id
embedding FLOAT_VECTOR dim=2
text      VARCHAR max_length=200
reference VARCHAR max_length=200
metadata  JSON
```

插入 3 条手写向量：

| 文本 | 向量 | reference |
| --- | --- | --- |
| `origin point` | `[0.0, 0.0]` | `manual-a` |
| `x axis near query` | `[1.0, 0.0]` | `manual-b` |
| `y axis farther` | `[0.0, 2.0]` | `manual-c` |

查询向量：

```text
[0.9, 0.0]
```

### 7.3 实验结果

Collection schema：

```text
collection= day5_milvus_l2_demo
description= Day 5 L2 demo collection
field= id type= 5 params= {}
field= embedding type= 101 params= {'dim': 2}
field= text type= 21 params= {'max_length': 200}
field= reference type= 21 params= {'max_length': 200}
field= metadata type= 23 params= {}
row_count= 3
```

检索结果：

```text
hit= x axis near query distance= 0.01 reference= manual-b metadata= {'label': 'B'}
hit= origin point distance= 0.81 reference= manual-a metadata= {'label': 'A'}
hit= y axis farther distance= 4.81 reference= manual-c metadata= {'label': 'C'}
```

解释：

- `[1.0, 0.0]` 离 `[0.9, 0.0]` 最近，平方 L2 是 `0.01`。
- `[0.0, 0.0]` 的平方 L2 是 `0.81`。
- `[0.0, 2.0]` 的平方 L2 是 `0.81 + 4 = 4.81`。

### 7.4 维度错误实验

用 3 维向量查 2 维 Collection：

```text
[0.9, 0.0, 0.0]
```

实际报错：

```text
vector dimension mismatch, expected vector size(byte) 8, actual 12
```

解释：

- 2 个 `float32` 是 8 bytes。
- 3 个 `float32` 是 12 bytes。
- Collection 要求 2 维，查询给了 3 维，所以 Milvus 拒绝搜索。

实验结束后删除临时 Collection：

```text
dropped= True
```

## 8. Milvus Lite 与 Docker Milvus 怎么选择

项目学习时你之前问过“不依赖 Docker，用 Milvus Lite 有什么区别”。面试可以这样回答：

| 方案 | 适合场景 | 优点 | 代价 |
| --- | --- | --- | --- |
| Milvus Lite | 本地学习、单机 demo、小数据验证 | 不依赖 Docker，启动简单 | 不适合模拟完整服务化部署能力 |
| Docker Milvus standalone | 本地完整服务、接近真实部署 | 有独立服务端、端口、组件、连接失败等真实运维问题 | 占内存，需要 Docker Desktop |
| 分布式 Milvus | 生产大规模数据和高并发 | 横向扩展、组件拆分 | 运维复杂，学习成本高 |

诚实边界：

> 当前学习项目用 Docker standalone 更能练到服务连接、schema、索引和故障恢复；如果只是写代码 demo，Milvus Lite 更轻便。但不能把 Lite 说成等同生产集群。

## 9. 为什么选择 Milvus，而不是普通数据库字段

普通数据库可以存文本，但不擅长高维向量近邻搜索。RAG 需要的问题是：

```text
给定一个查询向量，在大量文档向量中找最近的 top_k
```

Milvus 提供：

- 向量字段类型。
- 向量索引。
- L2/Cosine/IP 等距离度量。
- metadata/text/reference 一起返回。
- Collection 级组织。
- 可选 hybrid search。

代价是：

- 多一个外部服务。
- 需要管理 Collection schema 和模型维度。
- 需要处理连接失败、索引构建、数据迁移。
- 对小项目可能比 pgvector 或本地 FAISS 更重。

## 10. 核心面试题（优化版，先学这一组）

### 核心题 1：为什么使用 Milvus，和 FAISS、pgvector 如何取舍？

#### 一句话回答

Milvus 适合把向量检索作为独立数据服务；FAISS 更像单机检索库，pgvector 适合向量与关系数据统一管理。

#### 2～3 分钟回答

当前项目需要保存向量、文本、来源和 metadata，并按 Collection 检索，所以选择了提供持久化、索引和客户端接口的 Milvus。FAISS 轻量、适合本地算法实验，但持久化、权限和服务化要自己补；pgvector 能复用 PostgreSQL 的事务、SQL 和运维体系，数据规模中等且关系过滤重要时很有吸引力。选型不能只看“谁性能高”，还要看规模、过滤需求、团队运维能力和已有基础设施。

#### 面试官继续追问

- 数据只有几万条时，为什么不直接用 FAISS？
- 强事务和复杂关系过滤重要时会怎么选？
- 你用什么压测证明需要独立向量数据库？

#### 当前项目证据

DeepSearcher 的 VectorDB 抽象允许替换后端；当前 Milvus 实现负责建 Collection、建索引、插入和 top-k 搜索。

#### 诚实边界

项目没有完成三种方案的同条件基准测试，因此只能说明工程取舍，不能宣称 Milvus 在所有场景性能最好。

### 核心题 2：Milvus Lite 与 Docker Milvus 分别适合什么阶段？

#### 一句话回答

Lite 更适合低门槛本地实验和单元测试，Docker Milvus 更接近独立服务的部署与故障模式。

#### 2～3 分钟回答

Milvus Lite 省去容器和多个服务，适合个人学习、CI 小数据测试；Docker 版本通过网络访问，更容易演练连接、就绪、资源限制和服务重启，也更接近多人共享环境。Lite 的方便不代表生产能力，Docker 单机也不等于分布式生产集群。选择依据是学习目标：验证 API 可用时优先 Lite，学习服务运维和真实网络故障时用 Docker。

#### 面试官继续追问

- Lite 测试通过为什么不能证明 Docker 部署正常？
- Docker 端口可连接为什么仍可能未就绪？
- 本地开发如何减少两条路径的行为差异？

#### 当前项目证据

本次用 Docker Milvus 完成了真实建表、插入和搜索；仓库中的 Lite 测试因当前环境缺少 `milvus_lite` 依赖而失败。

#### 诚实边界

不能把 Docker 单机实验包装成高可用集群，也不能说“Milvus 测试全部通过”。

### 核心题 3：检索返回空结果，为什么不一定表示知识库没有答案？

#### 一句话回答

空结果既可能是真无命中，也可能来自连接失败、路由错误、维度不匹配、Collection 不存在或异常被吞掉。

#### 2～3 分钟回答

正确做法是把结果状态拆开：系统错误、没有可查询 Collection、查询成功但零命中、命中但低相关。当前适配层为了避免程序崩溃，会在部分异常后返回空列表，上层如果只看到 `[]` 就会丢失根因。生产接口应返回结构化错误码，并记录 collection、metric、维度、耗时和异常类型，同时避免在客户端泄露内部地址和 metadata。

#### 面试官继续追问

- 你会给“真无命中”和“向量库离线”返回相同 HTTP 状态吗？
- 怎样避免重试放大故障？
- 哪些字段适合进日志，哪些必须脱敏？

#### 当前项目证据

`list_collections()` 和 `search_data()` 的异常路径可能返回空列表；第 1 天也验证了 Milvus 离线时的表现。

#### 诚实边界

当前项目尚未完整区分所有失败类型，也没有熔断、退避重试和告警闭环。

### 核心题 4：Collection、索引、距离度量和向量维度怎样配合？

#### 一句话回答

Collection 固定数据结构和维度，索引决定如何加速候选搜索，metric 决定距离含义，查询向量必须满足同一约定。

#### 2～3 分钟回答

建表时先定义向量字段的 dimension，同时保存 text、reference 和 metadata；再为向量字段配置索引与 metric。插入时每条 Chunk 的向量长度必须匹配；搜索时 query vector 也必须同维，Milvus 才能按指定 metric 返回 top-k。索引提高速度通常会引入构建成本、内存占用或近似误差，因此需要根据数据量、延迟和召回率调参。

#### 面试官继续追问

- 为什么 schema 正确仍可能检索质量差？
- 精确检索和近似检索如何取舍？
- metric 和 Embedding 模型建议不一致会怎样？

#### 当前项目证据

临时 2 维 Collection 成功插入 3 条数据；L2 查询按距离排序；3 维向量查询时 Milvus 明确报维度不匹配。

#### 诚实边界

本次实验验证了正确性，没有完成不同索引类型、数据规模和参数下的 Recall/Latency 基准测试。

### 核心题 5：如果检索流量扩大十倍，你会先改什么？

#### 一句话回答

先测量瓶颈，再按查询、连接、索引和入库链路分别扩容，不能直接堆机器。

#### 2～3 分钟回答

我会先记录 QPS、P95/P99 延迟、错误率、每次 top-k、候选数量、连接数和资源使用，确认瓶颈在 FastAPI、Embedding、Milvus 还是 LLM。查询侧可做连接池、限流、缓存和索引调优；入库与查询可拆分，批量 Embedding 和写入走异步任务；数据量增长后再考虑分区、副本和集群容量。每一步都用压测和 Recall@K 回归验证，避免只优化延迟却损害召回。

#### 面试官继续追问

- 为什么缓存可能返回过期或越权结果？
- 限流应该放在哪一层？
- 扩副本能解决写入瓶颈吗？

#### 当前项目证据

当前链路已有独立 FastAPI、Embedding 服务调用和 Milvus 服务边界，具备分层测量基础；但本次仅做本地功能实验。

#### 诚实边界

限流、缓存、异步任务、集群副本和容量规划均是改造方向，当前项目没有验证十倍流量。

## 10.1 源码细节补充题（第二遍再看）

### Q1：Milvus Collection 在项目里相当于什么？

一句话回答：

> 相当于一张保存知识片段的向量表，里面有向量、文本、来源和 metadata。

深入回答：

> DeepSearcher 入库时会为每个 Collection 创建固定 schema，其中 `embedding` 是 `FLOAT_VECTOR(dim=...)`，`text` 保存 Chunk 文本，`reference` 保存来源，`metadata` 保存扩展上下文。查询时用 query vector 在 `embedding` 字段上做 top_k 搜索，再把命中的行转换成 `RetrievalResult` 给 RAG Agent 使用。

诚实边界：

> 当前项目没有在 schema 里显式保存 embedding model version，所以模型升级后的数据治理还比较粗糙。

### Q2：为什么必须建索引？

一句话回答：

> 索引用来让高维向量近邻搜索更高效，并定义搜索使用的 metric。

深入回答：

> 源码里通过 `prepare_index_params()` 给 `embedding` 字段添加索引，并设置 `metric_type="L2"`。小数据时暴力搜索也能跑，但数据量上来后需要索引减少搜索成本。索引选择和 metric 会影响召回速度、召回质量和分数解释。

诚实边界：

> 当前源码没有暴露复杂索引参数调优，也没有做大规模压测，所以不能声称索引参数已经生产最优。

### Q3：Milvus 返回的 score 是什么？

一句话回答：

> 在当前实现中它来自 Milvus 的 `distance`，如果 metric 是 L2，就应该解释为距离值。

深入回答：

> `search_data()` 把 `b["distance"]` 填进 `RetrievalResult.score`。这只是项目统一字段名，不代表一定是相似度。当前默认 metric 是 L2，本次实验里最近结果 distance 是 `0.01`，更远的是 `0.81` 和 `4.81`，说明值越小越近。

追问准备：

> 如果换成 Cosine 或 IP，就要按对应 metric 重新解释分数，不能混用说法。

### Q4：维度不一致会怎样？

一句话回答：

> Milvus 会拒绝插入或搜索，因为 Collection 的向量字段维度已经固定。

深入回答：

> 本次实验创建了 2 维 Collection，用 3 维查询向量搜索时，Milvus 报 `vector dimension mismatch, expected vector size(byte) 8, actual 12`。在真实项目里，如果入库用 1024 维 Embedding，查询却换成 1536 维模型，就会出现同类问题。所以切换 Embedding 模型时要重建 Collection 并重新入库。

### Q5：`force_new_collection=True` 有什么风险？

一句话回答：

> 它会删除已有 Collection 再重建，可能导致已有向量数据丢失。

深入回答：

> `init_collection()` 里如果发现 Collection 已存在并且 `force_new_collection=True`，会调用 `drop_collection()`。这在本地实验很方便，可以清理旧 schema；但生产环境必须非常谨慎，应该有迁移流程、备份和权限控制。

诚实边界：

> 当前项目没有内置防误删保护。

### Q6：Milvus 连接失败时系统会怎样？

一句话回答：

> VectorDB 方法会记录 critical 日志，部分方法返回空结果，但上层可能只看到没有 Collection 或没有检索结果。

深入回答：

> 例如 `list_collections()` 捕获异常后返回空列表，`search_data()` 捕获异常后返回空列表。这避免了程序直接崩溃，但也可能掩盖根因。更好的生产做法是把连接失败、空结果和真实无命中区分开，返回明确错误状态给 API 和前端。

## 13. 今天的 1 分钟表达模板

> Milvus 在项目里承担向量数据库角色。入库时，DeepSearcher 用当前 Embedding 模型的 `dimension` 创建 Collection，核心字段是 `embedding FLOAT_VECTOR(dim=...)`、`text`、`reference` 和 `metadata`，并在 `embedding` 字段上建立 L2 metric 的索引。插入时写入每个 Chunk 的向量和文本；查询时用同维度 query vector 做 top_k 搜索，返回的 `score` 实际来自 Milvus 的 distance。当前默认 L2 要解释成距离，越小越近。本次我用 2 维临时 Collection 实验过，3 条数据检索结果按距离 `0.01/0.81/4.81` 排序；如果用 3 维向量查 2 维 Collection，Milvus 会报维度不匹配。项目短板是异常被捕获后容易变成空结果，生产上应区分连接失败和真实无命中。
