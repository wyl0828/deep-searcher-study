## 0. 面试官友好版：先讲“PDF 怎么变成可检索文本”

这一篇不要一上来讲 `PDFLoader`、`Document`、`Chunk`。先讲人话：**系统先把 PDF 里的文字拿出来，再切成适合检索的小片段。**

30 秒人话版：

> 文档入库的第一步是把 PDF 变成纯文本。当前项目用一个轻量解析器读取 PDF 中能复制出来的文字，然后把整份文档作为原始文本保存下来。接着系统会把长文本切成多个较小片段，因为检索时不适合整篇文档一起查。每个片段会保留来源文件和一段更宽的上下文，后面做向量化和问答时就能知道答案来自哪里。这个实现简单直接，但它不是生产级 PDF 理解：扫描件、复杂表格、图片、页码级引用都没有完整处理。

术语降噪：

| 文档里会出现的词 | 面试时先翻译成 |
| --- | --- |
| PDFLoader | PDF 文本解析器 |
| Document | 原始文档文本 |
| Chunk | 文档切片 / 检索片段 |
| metadata | 附加信息 |
| reference | 来源文件路径 |
| wider_text | 命中片段周围的上下文 |
| splitter | 文本切分器 |

- 能不能给出答案所在页码？
- 扫描 PDF、表格、图片能不能处理？

- 诚实边界：默认实现没有 OCR、页码级引用和复杂版面理解。

## 1. 今天先记住一条链路

```text
本地文件：PDF / TXT / Markdown
  ↓ 读取文件里的文字
  （代码名：PDFLoader.load_file / load_directory）
原始文档文本：正文 + 来源路径
  （代码名：Document(page_content, reference)）
  ↓ 切成适合检索的小段
  （代码名：split_docs_to_chunks）
文档片段：片段文字 + 来源 + 周边上下文
  （代码名：Chunk(text, reference, wider_text)）
  ↓ 把每个片段变成语义向量
  （代码名：embedding_model.embed_chunks）
带向量的文档片段
  （代码名：chunk.embedding）
  ↓ 写入向量数据库
  （代码名：vector_db.insert_data）
向量知识库
  （代码名：Milvus Collection）
```

先按中文理解：文件 → 原始文本 → 文档片段 → 语义向量 → 向量知识库。英文代码名只是为了你回头能定位源码。

面试时不要只说“解析 PDF 后入库”。更准确的说法是：

> 当前项目先用 Loader 把原始文件转成 LangChain 的 `Document`，再由 splitter 切成项目自己的 `Chunk` 对象。Embedding 不直接处理 PDF 文件，而是处理 Chunk 文本；Milvus 保存的是 Chunk 的文本、来源、元数据和向量。

## 3. PDFLoader 做了什么

如果要追代码，可以看：`deepsearcher/loader/file_loader/pdf_loader.py`

当前 `PDFLoader` 支持三类文件：

```python
return ["pdf", "md", "txt"]
```

### PDF 文件

PDF 路径会走 `pdfplumber.open(file_path)`：

```text
每页 page.extract_text()
  ↓
用两个换行拼接所有页面文本
  ↓
返回 1 个 Document
```

返回对象形态：

```python
Document(
    page_content="整份 PDF 提取出的文本",
    metadata={"reference": file_path},
)
```

注意：当前实现不是“一页一个 Document”，而是“一份 PDF 一个 Document”。页码、表格结构、图片内容、标题层级不会被单独保留下来。

### TXT / Markdown 文件

TXT 和 Markdown 不走 `pdfplumber`，直接用 UTF-8 读取全文：

```python
with open(file_path, "r", encoding="utf-8") as file:
    page_content = file.read()
```

这意味着 Markdown 的标题、列表、代码块在这里都只是普通文本。后续 splitter 会按字符递归切分，不会理解 Markdown 语义结构。

## 4. BaseLoader 做了什么

如果要追代码，可以看：`deepsearcher/loader/file_loader/base.py`

`load_directory()` 会递归遍历目录，对文件名后缀做匹配：

```text
os.walk(directory)
  ↓
判断 file.endswith(suffix)
  ↓
调用 self.load_file(full_path)
  ↓
合并所有 Document
```

这个设计的好处是：不同 Loader 只要声明 `supported_file_types` 并实现 `load_file()`，就自动拥有目录加载能力。

代价是：

- 后缀匹配比较朴素，没有统一小写，`A.PDF` 这类大写后缀可能不会被加载。
- 不支持的文件类型不会报错提醒，只是不会被目录加载选中。
- 单文件 `load_file()` 如果传入不支持的后缀，当前 `PDFLoader` 没有显式 `raise`，可能返回 `None`，上层若未防御会产生后续异常。

## 5. Splitter 做了什么

如果要追代码，可以看：`deepsearcher/loader/splitter.py`

`split_docs_to_chunks()` 默认参数：

```python
chunk_size = 1500
chunk_overlap = 100
```

它内部使用：

```python
RecursiveCharacterTextSplitter(
    chunk_size=chunk_size,
    chunk_overlap=chunk_overlap,
)
```

切分后不是直接返回 LangChain `Document`，而是转换成项目自己的 `Chunk`：

```python
Chunk(
    text=doc_text,
    reference=reference,
    metadata={"wider_text": wider_text},
)
```

这里的 `wider_text` 是从原始全文中截取的前后文窗口，当前 offset 是 300 字符。也就是说：

- `chunk.text` 是真正被 Embedding 的文本。
- `chunk.reference` 是来源文件路径。
- `chunk.metadata["wider_text"]` 是检索命中后可提供给 LLM 的更宽上下文。
- `chunk.embedding` 此时还是 `None`，直到 `embedding_model.embed_chunks()` 才会被填充。

## 6. 本次真实实验记录

为了不重复消耗模型 API，本次只跑到 Loader 和 Splitter，不执行 Embedding 与 Milvus 写入。

实验命令：

```powershell
uv run --frozen python - <<'PY'

from deepsearcher.loader.file_loader import PDFLoader
from deepsearcher.loader.splitter import split_docs_to_chunks

paths = [

PY
```

在 PowerShell 中如果不使用 Bash 风格 here-doc，可以用：

实际结果：

| 文件 | Document 数 | 文本字符数 | `500/50` 切分 | 默认 `1500/100` 切分 |
| --- | ---: | ---: | ---: | ---: |
| `data/baseline/aurora-facts.pdf` | 1 | 209 | 1 | 1 |
| `examples/data/WhatisMilvus.pdf` | 1 | 10672 | 25 | 10 |

第一个 Chunk 的观察结果：

```text
reference = examples\data\WhatisMilvus.pdf
metadata keys = ["wider_text"]
chunk.text 长度 = 456
wider_text 长度 = 755
```

这证明了两个点：

1. Loader 只负责“提取全文和来源”，不负责生成向量。
2. `chunk_size` 会直接影响 Chunk 数量，从而影响召回颗粒度、Embedding 成本、Milvus 行数和 LLM 上下文长度。

实验中还看到 `pdfplumber` 输出了：

```text
CropBox missing from /Page, defaulting to MediaBox
```

这不是业务异常，而是 PDF 页面盒信息缺失时的解析警告。它提醒我们：PDF 是复杂格式，解析质量取决于 PDF 本身结构。

## 7. 为什么不直接整篇 PDF 做 Embedding

可以，但不适合大多数 RAG 场景。

如果整篇 PDF 只生成一个向量：

- 检索颗粒度太粗，用户问一个细节时也只能召回整篇。
- 文本太长时可能超过 Embedding 模型输入限制。
- 命中后塞给 LLM 的上下文太大，token 成本高。
- 多主题文档会被压成一个向量，语义会混在一起。

当前项目先切 Chunk，是为了让检索单元更小、更可控。代价是：

- Chunk 太小会丢上下文。
- Chunk 太大召回不精准。
- Overlap 太大增加重复向量和存储成本。
- 当前切分是通用字符切分，不理解 PDF 章节、表格和图片。

## 8. 核心面试题（优化版，先学这一组）

### 核心题 1：为什么不能把整篇 PDF 直接变成一个向量？

#### 一句话回答

整篇文档只有一个向量时检索颗粒度太粗，细节问题会带回大量无关内容，还会抬高生成成本。

#### 2～3 分钟回答

RAG 需要找与问题最相关的局部证据。整篇 PDF 做一个向量，文档中的多个主题会被压进同一表示，用户问一个细节也只能召回整篇。切成 Chunk 后，可以用较小片段做精准检索，再用 overlap 和 `wider_text` 补足边界上下文。切得太小会割裂语义、增加向量数量；切得太大又会降低精度并增加 Token，所以参数必须通过评测选择。

#### 面试官继续追问

- Chunk 越小，Recall@K 一定越高吗？
- overlap 太大会产生什么成本？
- 为什么检索用短片段，生成却可以用更宽上下文？

#### 当前项目证据

默认切分参数为 `1500/100`；同一份 `WhatisMilvus.pdf` 实测得到 10 个 Chunk，改成 `500/50` 后得到 25 个 Chunk。

#### 诚实边界

当前实验只证明参数会改变片段数量，没有用标注问题集比较 Recall@K 和回答质量，因此不能声称默认值最优。

### 核心题 2：切分大小和重叠应该怎样确定，而不是凭经验拍值？

#### 一句话回答

准备带标准证据片段的问题集，对多组参数比较 Recall@K、上下文完整性、延迟和 Token，再按业务目标取舍。

#### 2～3 分钟回答

我会选取事实问答、多跳问题、跨段问题和表格问题，为每题标注相关页或片段。然后固定 Embedding 和检索参数，只改变 chunk size 与 overlap，统计标准证据是否进入前 K、返回重复率、平均上下文长度、入库耗时和回答正确率。参数不是越大或越小越好：知识点密集的文档可能适合较小片段，章节型长文档可能需要结构化切分。

#### 面试官继续追问

- Recall@K 高但答案仍错，下一步查什么？
- 如何避免测试集和某一种文档类型绑定？
- 不同文档能否使用不同切分策略？

#### 当前项目证据

`split_docs_to_chunks()` 暴露 `chunk_size` 和 `chunk_overlap`，已有不同参数的片段数量实验，可作为后续离线评测的可控变量。

#### 诚实边界

项目当前没有自动切分评测、动态参数选择或按文档结构自适应策略；这里描述的是验证方法，不是已完成结果。

### 核心题 3：为什么扫描件、表格和多栏 PDF 容易解析失败？

#### 一句话回答

默认解析器主要抽取文本层，不理解图片中文字、版面阅读顺序和表格结构。

#### 2～3 分钟回答

普通文本 PDF 可以直接提取字符，但扫描件只有图片，需要 OCR；多栏排版可能按错误顺序拼接文字；表格如果丢失行列关系，后续切分得到的文本即使能检索，也可能无法还原含义。更完整的方案会先识别文档类型，再选择 OCR、版面分析或表格抽取，并把页码、区域和章节写进 metadata。代价是依赖更重、处理更慢、错误类型也更多。

#### 面试官继续追问

- OCR 有结果为什么仍可能答错？
- 表格应该转成纯文本、Markdown 还是结构化数据？
- 怎样评测解析质量？

#### 当前项目证据

默认 `PDFLoader` 使用 `pdfplumber.extract_text()`，把各页文字拼成一份 `Document`；仓库虽有其他 Loader 选项，但默认链路没有 OCR 和版面理解。

#### 诚实边界

不能把当前能力描述成“支持所有 PDF”；它更适合有可复制文本、排版相对简单的文档。

### 核心题 4：如果面试官要求答案显示页码或章节，你会怎样改？

#### 一句话回答

解析阶段按页或章节产生文档单元，把页码、章节和稳定位置写进 metadata，并让检索结果和最终回答携带这些引用。

#### 2～3 分钟回答

当前一份 PDF 先合并成一个 `Document`，来源主要精确到文件。要支持页码引用，解析器应保留页边界；切分时把 `page_number`、`section_title`、字符 offset 等信息传入 Chunk；入库时原样保存 metadata；检索和生成接口再返回引用。这样不仅方便用户核验，也能帮助排查错误召回。代价是跨页段落和跨章节表格需要额外合并策略。

#### 面试官继续追问

- 一个 Chunk 横跨两页，页码怎么展示？
- 引用存在是否就能证明答案受证据支持？
- 如何防止模型编造不存在的页码？

#### 当前项目证据

现有 Chunk 已保存 `reference` 和 metadata，具备扩展字段的基础；但默认 PDF 流程没有稳定页码和字符 offset。

#### 诚实边界

当前只能较可靠地说明来源文件，不能声称已经实现页码级、句子级引用或引用正确率评测。

## 8.1 源码细节补充题（第二遍再看）

### Q1：PDFLoader 解析后直接写入 Milvus 吗？

一句话回答：

> 不是。PDFLoader 只产出 `Document`，真正写入 Milvus 前还要经过 splitter 切 Chunk、Embedding 生成向量，再由 `vector_db.insert_data()` 写入。

深入回答：

> 源码上，`offline_loading.load_from_local_files()` 先调用 `file_loader.load_file()` 或 `load_directory()` 得到 `Document` 列表；然后调用 `split_docs_to_chunks()` 生成 `Chunk`；接着 `embedding_model.embed_chunks()` 给每个 Chunk 填充向量；最后 `vector_db.insert_data()` 将文本、来源、metadata、embedding 写入 Collection。这样设计让 Loader 不关心向量库，也让不同文件解析器可以复用同一套入库流程。

诚实边界：

> 当前 Loader 没有保留页码、图片 OCR、复杂表格结构，所以不能说它已经实现了高质量 PDF 版面理解。

### Q2：为什么当前项目“一份 PDF 一个 Document”，不是“一页一个 Document”？

一句话回答：

> 这是一个简单实现：先提取整篇文本，再统一交给 splitter 切分。

深入回答：

> 好处是实现简单，不需要在 Loader 层处理跨页上下文，后续 `RecursiveCharacterTextSplitter` 可以统一切分所有文本。代价是页码、章节、页面边界会丢失，引用也只能精确到文件路径，无法回答“第几页证据在哪里”。如果要做面试级优化，我会改成按页或按章节生成 `Document`，metadata 里加入 `page_number`、`section_title`，检索结果再展示更具体的引用。

追问准备：

> 如果文档很短，比如 `aurora-facts.pdf` 只有 209 个字符，一份 PDF 一个 Document 没问题；但长 PDF，比如 `WhatisMilvus.pdf` 有 10672 个字符，后面必须切 Chunk，否则召回和成本都会出问题。

### Q3：`chunk_size=1500` 和 `chunk_overlap=100` 为什么这样设？

一句话回答：

> 这是工程默认值，试图在召回颗粒度、上下文完整性和成本之间折中。

深入回答：

> `chunk_size` 越大，单个向量包含的信息越多，但检索颗粒度更粗，LLM 上下文成本更高；`chunk_size` 越小，召回更精细，但上下文容易断裂，Milvus 行数和 Embedding 成本会上升。`chunk_overlap` 用来缓解切分边界导致的信息断裂，但过大就会产生大量重复。我们本次实测 `WhatisMilvus.pdf` 默认 `1500/100` 是 10 个 Chunk，改成 `500/50` 是 25 个 Chunk。

诚实边界：

> 当前项目没有基于评测集自动调参，所以不能说 1500/100 是最优，只能说是默认经验参数。真正上线应该用召回率、答案准确率、延迟和 token 成本做网格实验。

### Q4：`wider_text` 有什么用？

一句话回答：

> `wider_text` 是命中 Chunk 周围的上下文窗口，用来弥补 Chunk 本身过短导致的上下文不足。

深入回答：

> splitter 先把文档切成小段，每个小段作为 `chunk.text`；再从原始全文里按位置向前后扩展一段，保存到 `metadata["wider_text"]`。这样检索可以用较短文本保持精准，生成回答时又能给 LLM 更完整的局部上下文。

诚实边界：

> 当前实现用 `original_text.index(doc_text)` 找位置，如果文档中有重复片段，理论上可能定位到第一个相同片段。它没有维护稳定的字符 offset，也没有页码级定位。

### Q5：当前 PDF 解析最大的问题是什么？

一句话回答：

> 最大问题是只做文本抽取，不做版面理解、OCR、结构化表格和页码级引用。

深入回答：

> `pdfplumber.extract_text()` 对可复制文本 PDF 比较方便，但扫描件、复杂表格、多栏排版、脚注、图片和公式都可能丢信息或顺序错乱。当前项目还有 DoclingLoader、UnstructuredLoader 等可替代方案，但默认 `PDFLoader` 是轻量路线，不等于生产级文档解析。

可替代方案：

- 用 Docling 做更强的结构化解析。
- 用 Unstructured 做多格式文档解析。
- 对扫描 PDF 加 OCR。
- metadata 加页码、章节、标题层级。
- 对表格单独抽取成结构化文本或 Markdown 表格。

## 10. 今天的 1 分钟表达模板

> 离线入库这块，我先从 Loader 看起。当前默认 `PDFLoader` 用 `pdfplumber` 把 PDF 的每页文本抽出来并拼成一个 LangChain `Document`，metadata 里保留来源文件路径。然后 `split_docs_to_chunks()` 用 `RecursiveCharacterTextSplitter` 按默认 `1500/100` 切成项目自己的 `Chunk`，每个 Chunk 包含文本、来源和 `wider_text` 上下文窗口。再往后才是 Embedding 和 Milvus 写入。这个设计让文件解析、文本切分、向量化、存储解耦，但当前 PDF 解析比较轻量，没有页码级引用、OCR、表格结构和版面理解，所以不能把它包装成生产级文档理解系统。
