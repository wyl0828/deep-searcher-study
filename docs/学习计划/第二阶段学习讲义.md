## 1. FastAPI 业务入口：把 HTTP 请求接到 DeepSearcher

### 1.1 先记住一条中文链路

```text
客户端 HTTP 请求
→ FastAPI 解析并校验参数
→ main.py 选择配置、入库或查询函数
→ online_query.py 读取当前全局 Searcher
→ RAGRouter 选择 DeepSearch 或 ChainOfRAG
→ LLM、Embedding、Milvus 完成查询
→ main.py 把结果或异常转换成 HTTP 响应
```

FastAPI 解决的是“怎样把 Python 业务能力安全、稳定地暴露成网络接口”，它本身不负责 RAG。`main.py` 是 HTTP 适配层，`deepsearcher/online_query.py` 是很薄的业务门面，Agent、Embedding 和 Milvus 才是查询主体。

### 1.2 应用启动时发生什么

`main.py` 先调用 `load_dotenv()`，让后续创建模型客户端时能够读取 `.env` 中的密钥和地址；然后创建 `FastAPI` 应用、读取 YAML 配置，并在模块导入阶段立即调用 `init_config(config)`。

`init_config()` 会同步创建：

- LLM 客户端。
- Embedding 客户端。
- 文件加载器和网页爬虫。
- VectorDB 客户端。
- 由 DeepSearch 和 ChainOfRAG 组成的默认 RAGRouter。
- 作为基础能力保留的 NaiveRAG。

这样设计对单进程本地演示很直接：只要导入应用，后面的接口就能使用全局组件。代价是模块导入与外部依赖初始化绑在一起，测试仅仅 `import main` 也可能等待真实组件；启动失败也难以区分是应用代码、模型配置还是 Milvus 连接问题。更可控的替代方案是使用 FastAPI lifespan 在启动阶段创建资源，通过依赖注入把服务传给接口，并在关闭阶段释放连接。

当前还有两个容易忽略的事实：

1. `main.py` 有自己的 `config = Configuration()`，`deepsearcher.configuration` 模块也有一个同名配置对象；实际传给 `init_config()` 的是 `main.py` 的对象。
2. `/set-provider-config/` 只修改当前进程内存中的配置，没有把改动写回 `config.yaml`。重启后会恢复文件配置，多 Uvicorn worker 之间也不会自动同步。

### 1.3 四个业务接口分别做什么

| 接口 | 输入位置 | 当前作用 | 关键边界 |
| --- | --- | --- | --- |
| `POST /set-provider-config/` | JSON Body | 修改某类 provider 配置并重建全部全局组件 | 进程内生效；无鉴权；响应可能原样回显包含密钥的 `config` |
| `POST /load-files/` | JSON Body | 读取后端机器上的文件路径，切 Chunk、Embedding 后写入 Milvus | 不是浏览器二进制上传接口；默认 `batch_size=256` |
| `POST /load-website/` | JSON Body | 抓取 URL、切 Chunk、Embedding 后写入 Milvus | 依赖爬虫和外部网络；当前入口没有暴露抓取超时等治理参数 |
| `GET /query/` | Query String | 调用默认 RAGRouter 查询，可选返回 Trace | 问题会出现在 URL；返回的是最终答案和 Token，不返回检索结果 |

Pydantic 模型 `ProviderConfigRequest` 会校验 `feature`、`provider` 和 `config` 三个字段是否存在以及基本类型。其他接口通过 `Body()` 和 `Query()` 声明参数。比如 `max_iter` 设置了 `ge=1`，传入 `0` 时请求会在进入业务函数之前被 FastAPI/Pydantic 拒绝，通常返回 422。

但“类型校验通过”不等于“业务输入安全”。例如：

- `feature` 只是普通 `str`，是否受支持要到 `set_provider_config()` 才判断。
- `paths` 没有目录白名单，能否读取完全取决于服务进程的文件权限。
- `collection_name` 没有在 API 层定义完整命名规则。
- `original_query` 没有长度、内容和成本预算限制。
- 所有业务接口都没有身份认证和授权。

`main.py` 还提供 `--enable-cors` 开关，但它只在直接执行 `python main.py`、进入 `if __name__ == "__main__"` 分支时添加 CORS 中间件；常见的 `uvicorn main:app` 启动方式不会执行这段代码。并且 `argparse` 使用 `type=bool`，字符串 `"False"` 在 Python 中仍会转换为真值。当前开启后又允许任意 origin、method 和 header，不应把它当成生产级跨域策略。更稳妥的做法是用 `store_true` 或配置项，并显式列出可信前端 origin。

### 1.4 一个查询请求怎样进入 DeepSearcher

假设客户端请求：

```http
GET /query/?original_query=Milvus%20适合什么场景&max_iter=3&include_trace=true
```

完整执行顺序是：

1. FastAPI 把三个查询参数转换为 `str`、`int` 和 `bool`，并检查 `max_iter >= 1`。
2. `perform_query()` 看到 `include_trace=True`，调用 `query_with_trace(original_query, max_iter)`。
3. `query_with_trace()` 创建 `TraceCollector`，从 `deepsearcher.configuration.default_searcher` 读取当前 RAGRouter。
4. RAGRouter 先让 LLM 在 DeepSearch 与 ChainOfRAG 中选择一个 Agent。
5. 被选中的 Agent 做 Collection 路由、Embedding、Milvus 检索和答案生成，并把受控应用事件写入 Collector。
6. `query_with_trace()` 返回 `(answer, retrieval_results, consume_tokens, trace)`。
7. `perform_query()` 丢弃第二项检索结果，只向客户端返回 `result`、`consume_token` 和 `trace`。

未要求 Trace 时，入口调用 `query()`，响应保持原有结构：

```json
{
  "result": "……",
  "consume_token": 1234
}
```

`online_query.py` 没有在导入时复制 `default_searcher`，而是在每次调用时读取 `configuration.default_searcher`。这使配置切换后新请求能拿到新对象，但也带来并发代际问题：请求 A 可能已经拿到旧 Searcher，请求 B 重建全局对象后再拿到新 Searcher。单次调用中的局部变量仍指向旧对象，不会凭空变成新对象，但系统会暂时存在新旧两套客户端，且切换过程没有锁、版本号和原子发布协议。

### 1.5 文件入库请求怎样执行

`POST /load-files/` 接收的是一个后端可见路径或路径列表，而不是文件字节。入口把参数交给 `load_from_local_files()` 后，执行：

```text
路径存在性检查
→ 文件或目录解析为 Document
→ 按 1500/100 默认参数切 Chunk
→ 按 batch_size 批量生成 Embedding
→ 写入指定或默认 Collection
```

例如请求体：

```json
{
  "paths": ["D:/knowledge/a.pdf", "D:/knowledge/b.pdf"],
  "collection_name": "interview_notes",
  "batch_size": 64
}
```

这里的路径必须存在于 FastAPI 服务所在机器。浏览器用户电脑上的 `C:/Users/.../a.pdf` 对部署在另一台服务器上的后端没有意义。这正是后续本地代理需要先接收浏览器文件、保存临时文件，再把“后端可见路径”传给该接口的原因。

当前入口没有暴露 `chunk_size`、`chunk_overlap` 和 `force_new_collection`，因此 API 入库固定使用底层函数默认的 `1500/100`，并默认不删除 Collection。这减少了误操作入口，但也降低了调参灵活性。

### 1.6 `def` 与 `async def` 在这里有什么区别

当前四个路由函数都是普通 `def`。在本项目锁定的 FastAPI 0.115.12 / Starlette 0.46.2 中，FastAPI 会在线程池中执行同步路由，避免它们直接占住主事件循环。

必须区分三句话：

1. **`def` 会被放入线程池**：其他异步连接仍有机会被事件循环处理。
2. **线程池不等于无限并发**：一个长时间等待 LLM、Embedding 或 Milvus 的请求会持续占用一个工作线程；线程耗尽后新请求仍要排队。
3. **把签名改成 `async def` 不会自动变快**：如果函数内部仍直接调用同步 `llm.chat()`、`embed_query()` 和 Milvus 客户端，反而会直接阻塞事件循环。

正确选择取决于依赖：

- 依赖只有同步客户端：保留 `def`，或显式放入容量受控的线程池，并配置超时与并发上限。
- 依赖提供真正异步客户端：使用 `async def`，每层都 `await`，并把取消和 deadline 向下传播。
- PDF 解析等 CPU 密集任务：线程受 Python GIL 和 CPU 竞争影响，更适合任务队列或进程池，而不是占用 Web 请求线程。
- 大批量入库：更适合提交后台任务并返回 task ID，由 Worker 完成解析、Embedding 和写库。

当前 DeepSearch 内部虽然出现 `asyncio.gather()`，但其中仍包含同步模型和向量库调用，所以不能把整个系统描述成“异步高并发架构”。

### 1.7 异常怎样变成 HTTP 响应

当前有两层异常行为：

1. 请求缺字段、类型错误或 `max_iter < 1`，由 FastAPI/Pydantic 在进入业务函数前返回 422。
2. 进入业务函数后发生的任何 `Exception`，都被入口捕获并转换成 `HTTPException(status_code=500, detail=str(e))`。

第二层实现简单，却不稳定：文件不存在、非法 feature、上游限流、模型鉴权失败、Milvus 不可用和代码 Bug 都会变成 500；同时 `str(e)` 可能泄漏内部路径、供应商响应或连接信息。`/set-provider-config/` 成功时还会把 `request.config` 原样返回，如果其中包含 `api_key`，密钥就会出现在响应、浏览器状态或代理日志里。

更稳健的映射应先建立错误分类，例如：

| 场景 | 建议状态 | 稳定错误码示例 |
| --- | --- | --- |
| 参数语义不合法 | 400/422 | `INVALID_ARGUMENT` |
| 文件不存在 | 404 | `SOURCE_NOT_FOUND` |
| Collection 状态冲突 | 409 | `COLLECTION_CONFLICT` |
| 上游模型限流 | 429 或受控 503 | `UPSTREAM_RATE_LIMITED` |
| LLM、Embedding、Milvus 暂时不可用 | 502/503 | `DEPENDENCY_UNAVAILABLE` |
| 请求超过 deadline | 504 | `QUERY_TIMEOUT` |
| 未分类内部错误 | 500 | `INTERNAL_ERROR` |

客户端响应只返回稳定 `code`、安全 `message` 和 `request_id`；服务端日志记录完整堆栈和依赖错误，并对密钥、绝对路径和文档内容脱敏。还要注意，如果以后在当前 `try` 内主动抛出 `HTTPException`，宽泛的 `except Exception` 也可能把它重新包装成 500，因此应先 `except HTTPException: raise`，再处理领域异常和未知异常。

### 1.8 相关 API 测试实际保护了什么

当前 `tests/test_query_api.py` 有两个测试，通过 monkeypatch 替换 `main.query` 或 `main.query_with_trace`，再直接调用 `perform_query()`：

- 不请求 Trace 时，保护旧响应只有 `result` 和 `consume_token`。
- 请求 Trace 时，保护响应额外包含 `trace`。

它们能防止返回结构回归，但没有经过 ASGI、HTTP 参数解析和 Pydantic 校验，因此没有验证：

- URL 到函数参数的转换。
- `max_iter=0` 是否返回 422。
- 业务异常的状态码和安全响应。
- 配置、文件入库和网页入库接口。
- CORS、认证、超时、并发配置切换。
- 应用启动和依赖关闭。

而且测试文件在 monkeypatch 之前就 `import main`，会触发真实 `init_config()`。本次按当前工作区运行该测试时，测试在合理等待时间内没有完成，因此已终止，没有把它记成“测试通过”或“测试失败”。准确说法是：当前测试设计仍受启动期外部组件初始化影响，必须先解耦依赖，才能得到稳定的 API 单元测试。

合理的测试分层是：

1. 纯函数单元测试：直接测试错误分类和响应 DTO。
2. FastAPI `TestClient`/ASGI 测试：覆盖 200、422、404、503、504 和响应脱敏。
3. 集成测试：使用可控的测试 Milvus 与模型 Stub，验证完整调用链。
4. 并发测试：配置切换与查询同时发生时，验证版本隔离和资源回收。

### 1.9 为什么当前方案仍有价值，以及替代方案的代价

当前单文件入口适合学习和本地 Demo：代码少、调用链直、Swagger 文档可自动生成，也容易从函数跳进业务代码。若过早拆成很多 Controller、Service、Repository，反而会增加理解成本。

但当目标变为多人、多租户或生产服务时，需要付出结构化成本：

- lifespan 和依赖注入增加代码层次，但换来可测试的资源生命周期。
- 任务队列增加部署组件和状态管理，但避免大文件入库拖垮 Web 线程。
- 领域错误模型需要维护映射表，但客户端才能可靠重试和提示。
- 配置中心或版本化配置增加基础设施，但多 worker 和多实例才能一致。
- 认证、路径白名单与密钥脱敏增加开发工作，却是公开服务的基本安全边界。

### 1.10 常见错误说法

| 错误说法 | 正确说法 |
| --- | --- |
| FastAPI 接口是 `def`，所以一定阻塞整个服务 | 同步路由通常在线程池执行，不直接阻塞事件循环，但会占用有限工作线程 |
| 改成 `async def` 就能提高并发 | 只有整条依赖链真正异步并正确 `await` 才可能改善并发 |
| `/load-files/` 是文件上传接口 | 它接收后端文件系统路径，不接收文件字节 |
| 配置接口修改了 YAML | 它只修改当前进程内存并重建全局对象 |
| 所有错误返回 500 很统一 | 这会混淆客户端错误、依赖故障和服务 Bug，也不利于重试 |
| 有两个 monkeypatch 测试就证明 API 可用 | 当前测试只覆盖函数返回形状，没有覆盖真实 HTTP 和依赖生命周期 |
| 使用多个 Uvicorn worker 就能共享新配置 | 每个 worker 是独立进程，内存配置不会自动同步 |

### 1.11 面试标准表达

> DeepSearcher 的 FastAPI 入口是 HTTP 适配层。应用当前在导入 `main.py` 时读取配置并初始化 LLM、Embedding、Milvus 和默认 RAGRouter。查询接口经过参数校验后调用 `online_query.py`，后者读取当前全局 Searcher，由 RAGRouter 在 DeepSearch 与 ChainOfRAG 之间选择，再返回答案、Token 和可选的结构化 Trace。四个业务路由目前都是同步 `def`，FastAPI 会把它们放在线程池执行，但同步模型和向量库调用仍会占用有限线程；简单改成 `async def` 不能解决问题。当前实现适合单用户本地演示，生产化还需要依赖注入和生命周期管理、版本化配置、认证授权、超时限流、后台入库任务，以及稳定且脱敏的领域错误响应。

### 1.12 当前项目的诚实边界

- 已有可读的配置、文件入库、网页入库、查询和可选 Trace 接口。
- 已有 FastAPI/Pydantic 基础参数校验，但没有完整业务校验、认证与授权。
- 当前是同步阻塞依赖加线程池承载，不是端到端异步架构。
- 配置切换是进程内全局替换，没有并发版本隔离，也没有多 worker 同步。
- 文件接口读取服务端路径，不是可直接公开给远程浏览器的安全上传方案。
- 业务异常目前统一变成带原始错误文本的 500，尚未实现稳定错误协议和脱敏。
- 当前 API 测试只保护查询返回结构，而且仍与导入期真实依赖初始化耦合。
- CORS 只在直接运行脚本时按命令行参数安装，启动方式不同会得到不同策略，且当前策略过于宽泛。
- 没有负载测试数据，不能声称当前接口已经达到生产级吞吐、可用性或安全性。
