## 0. 执行决策

本轮工程化优化开始前，先完成当前 `v0.3.0-rc.1` 的既有评测收尾：

1. 从已有 checkpoint 续跑剩余 DeepSearch 2 题；
2. 完成 ChainOfRAG 24 题；
3. 生成并校验最终报告；
4. 保存当前配置、数据集、报告和已知失败，冻结为工程改造前基线；
5. 不在该评测任务中追加新功能或扩大评测范围。

完成基线冻结后再开始本文件中的 Ragent 对照优化。这样可以用同一基线判断工程改造是否造成检索、回答、引用或 Trust 回退。

本轮优化采用以下硬约束：

- **稳定优先**：先保证现有功能不回退，再增加工程能力；
- **一一对照**：只实现 Ragent 参考提交中已经存在、且本项目有直接对应场景的能力；
- **最小改写**：Java 代码按 Python 技术栈做等价改写，不顺便扩展新的架构层；
- **不超前补强 Ragent**：Ragent 自身尚未闭环的 Agent、Pipeline、消息幂等和分布式熔断，本轮不自行设计增强版；
- **不扩大产品范围**：不新增与当前知识库问答主链无关的业务功能；
- **测试跟随改动**：只补本次改动的回归测试和关键失败测试，不另建一套更复杂的平台。

## 1. 背景与目标

DeepSearcher Study 当前已经具备混合检索、多类 RAG Agent、声明级引用、Citation Span、确定性一致性检查、时效与风险策略、Trust Provenance、版本化评测以及可用的中文工作台。它的主要优势是可信回答和可复现验证，但默认部署仍依赖 SQLite、本地文件和单机 Worker，企业工程化与多实例运行能力不足。

本轮分析以 Ragent 的真实源码为主要工程参考，不只依据 README 或项目宣传。目标是：

1. 识别 Ragent 已经落地且适合 Python/FastAPI 等价改写的工程机制；
2. 按最小范围补齐 DeepSearcher Study 的共享状态、异步任务、模型容错和长期记忆；
3. 保留本项目已有的 Trust Layer、索引 Manifest 和评测优势；
4. 明确暂不优化的方向，避免项目演变成技术名词拼装或 Ragent 的 Python 翻版；
5. 为后续实现提供范围、顺序和最小验收标准，本文件本身不授权或包含实现修改。

## 2. 分析原则

### 2.1 以源码为准

- Ragent 源码存在、进入真实调用链且有测试或配置支撑的能力，可以作为主要参考；
- 只有 README、课程介绍或未来规划的能力，不视为已落地；
- Java/Spring 专属机制只提取业务语义和状态流转，使用 Python 生态进行等价改写；
- 不默认 Ragent 的实现完全正确，发现未闭环或仅单进程有效的部分必须单独记录；
- 对 Ragent 未闭环部分只保留边界说明，本轮不自行补成更复杂的增强方案；
- 后续若更新 Ragent，必须记录新提交并重新核对结论，不能让本文件随上游变化而静默失真。

### 2.2 不虚构生产能力

- 本地启动多个副本只能证明“支持多实例部署”，不能直接宣称高可用集群；
- 引入 PostgreSQL、Redis、RocketMQ 或 S3 兼容存储不等于完成分布式落地；
- 必须通过与本次改动直接相关的回归和关键失败测试证明机制有效；
- 第一版进程内熔断只能描述为模型熔断，不能描述为分布式熔断。

### 2.3 保留项目主线

本项目继续定位为“可追溯的企业知识库问答系统”。工程优化服务于可信问答的真实落地，不以堆叠 MCP、知识图谱、微服务和 Provider 数量为目标。

## 3. Ragent 源码核验结论

### 3.1 已进入真实调用链的能力

Ragent 当前主问答链路为：

```text
会话记忆加载
→ 问题重写与拆分
→ 意图解析与歧义引导
→ 知识库多通道检索 / MCP 工具调用
→ Prompt 组装
→ 模型候选路由与流式输出
→ 来源、Grounding Chunk、消息和 Trace 持久化
```

源码中可以确认的主要机制包括：

- PostgreSQL 业务数据存储；
- S3 兼容存储与阿里云 OSS 抽象；
- RocketMQ 事务消息、本地事务回调及基于数据库状态的事务回查；
- 向量、关键词、图谱和联网搜索通道的并行调度、超时隔离、融合与 Rerank；
- 最近 N 轮消息与持久化滚动摘要；
- MCP 工具发现、参数提取和调用；
- 候选模型路由、首包探测、Fallback 与三态熔断；
- Redis 公平排队、可过期许可及跨节点流式取消；
- S3/OSS 文件服务、管理后台、Trace 与业务审计。

### 3.2 不能视为成熟实现的能力

源码核验同时发现以下边界：

1. `agent` 模块在参考提交中只有 `pom.xml`，完整 ReAct Agent 执行代码尚未落地；
2. 可编排 Ingestion Pipeline 虽有引擎、节点和日志结构，但知识库主入库链路会明确返回“管道模式重构中，暂不可用”；
3. MQ 幂等切面已经实现，但当前仓库未发现 `@IdempotentConsume` 的实际使用点；
4. 文档 Consumer 调用的处理方法会捕获异常并标记失败，但不会继续将异常抛给 Broker，自动消费重试语义没有完全闭环；
5. 模型熔断状态保存在单个 JVM 的 `ConcurrentHashMap`，多实例之间不共享；
6. RocketMQ 事务消息只保证上游本地事务与消息投递的一致性，不能替代下游消费幂等、重试和补偿；
7. Ragent 的 Pipeline、幂等和熔断设计可以参考，但不能未经验证逐行翻译。

## 4. 当前项目的主要差距

| 领域 | DeepSearcher Study 当前状态 | 主要差距 |
| --- | --- | --- |
| 业务数据库 | SQLAlchemy + Alembic，默认 SQLite | 多实例并发、事务抢占和正式数据库验证不足 |

## 5. 本轮按 Ragent 对照优化的方面

### 5.1 PostgreSQL 作为正式业务数据库

#### 目标

将用户、知识库、文档、入库任务、会话、消息、引用、Trust 结果和索引版本状态迁移到 PostgreSQL，使多个 API 和 Consumer 访问同一份一致状态。

#### 改造内容

- 保留 SQLAlchemy 2 和 Alembic；
- 将默认正式部署数据库切换为 PostgreSQL，SQLite 仅保留为轻量开发或单元测试选项；
- 审查现有 SQLite 专属初始化、修复逻辑和 SQL；
- 任务抢占使用 PostgreSQL 行锁或等价的条件更新语义；
- 沿用 Ragent 的 PostgreSQL 持久化方向，保持现有唯一约束和事务边界；
- 为升级、回滚和已有 SQLite 数据迁移提供明确步骤。

#### 验收标准

- PostgreSQL 上完成全新迁移和已有数据迁移测试；
- 现有创建、查询、上传、问答和任务状态测试在 PostgreSQL 上通过；
- 原有 Trust、Citation 和 Manifest 数据契约不回退。

### 5.2 S3 兼容对象存储

#### 目标

解除 PDF 与本机路径的绑定，使任意 API 或 Consumer 都能读取同一份原始文档。

#### 参考结构

```text
文档业务服务
→ FileStorageService
→ ObjectStorage
   ├─ S3CompatibleStorage（MinIO / RustFS / S3）
   └─ 可选本地开发实现
```

#### 改造内容

- 对照 Ragent 抽象上传、读取、删除和受控下载能力；
- 正式部署使用 S3 兼容存储，本地开发实现不能进入多实例部署声明；
- 数据库保存 `bucket`、`object_key`、SHA-256、大小、媒体类型和治理元数据，不保存机器绝对路径；
- API 负责安全上传，Consumer 负责从对象存储流式读取；
- 保留文件大小、PDF 结构、页数、安全文件名、配额和重复文件校验；
- 文档或知识库删除沿用现有删除语义并同步删除对象；
- 历史引用保存证据快照，原文读取继续遵守权限和删除语义。

#### 验收标准

- 上传、处理、原文预览和删除在 S3 兼容存储上通过；
- 服务重启和本地工作目录变化不影响原文读取；
- 重复上传、删除失败和对象不存在都有明确状态；
- 保留现有文件大小和安全校验，不额外扩展新的上传协议。

### 5.3 RocketMQ 事务消息入库链路

#### 决策

主方案参考 Ragent 的 RocketMQ 事务消息，不默认替换成自定义 Outbox。Apache RocketMQ 5.x 官方统一 Python 客户端已声明支持事务消息 Producer，后续实现前仍需通过最小技术验证确认目标版本、Broker、Proxy 和 Python SDK 的接口可用性。

#### 目标流程

```text
上传对象成功并创建文档记录
→ Producer 发送 Half Message
→ Broker 持久化但暂不投递
→ 本地数据库事务将文档置为 RUNNING
→ 本地事务成功则 Commit，失败则 Rollback
→ 二次确认丢失时，Broker 根据 document_id 回查 PostgreSQL
→ Commit 后 Consumer 执行解析、分块、Embedding、候选索引写入与切换
```

#### 事务回查

- 对照 Ragent，以消息中的 `document_id` 查询 PostgreSQL 文档状态；
- 文档已经进入 Ragent 对应的运行状态时返回 `COMMIT`，否则返回 `ROLLBACK`；
- SDK 或数据库查询异常时使用官方客户端支持的未知结果语义；
- 不在本轮额外设计一套新的事务状态机。

#### 验收标准

- Half Message 发送失败时不执行本地业务事务；
- 本地事务失败时消息不可被 Consumer 看见；
- Commit 确认丢失时 Broker 回查能得到正确状态；
- Producer 重启后回查不依赖原进程内存；
- 事务消息 Topic 类型和必要连接参数显式配置；
- 文档状态与可投递消息最终一致。

### 5.4 保留现有任务稳定性，不新建消息状态系统

Ragent 参考提交虽然存在 MQ 幂等切面，但没有找到实际注解用例；文档 Consumer 失败后也没有形成完整的 Broker 重试闭环。因此本轮不自行增加一套比 Ragent 更复杂的消息状态机、幂等事件表或人工核对平台。

本轮只做以下最小衔接：

- Consumer 收到消息后复用现有文档状态检查，已完成任务直接结束；
- 继续使用现有 Manifest、文档 SHA-256、候选索引和版本切换，避免明显重复写入；
- 保留当前已有的失败状态、重试次数和死信字段，不扩展新状态枚举；
- 按 Python RocketMQ 客户端的既有成功/失败返回方式处理消费结果；
- 只测试重复消息不会破坏已经完成的文档和有效索引。

若后续真实运行证明 Ragent 同等实现无法满足稳定性，再单独立项分析消费幂等，不在本轮提前建设。

### 5.5 模型候选路由、首包检测和熔断

#### 目标

将当前“配置一个 Provider”提升为“运行时按能力和优先级选择候选模型，并在故障时自动切换”。

#### 改造内容

- 对照 Ragent，先为 Chat 定义候选列表；Embedding、Rerank 和 Checker 保持现有配置，本轮不同时扩展；
- 按能力、档位、优先级及显式指定模型筛选；
- 同步调用失败时切换下一候选；
- 流式调用必须等待有效首包，超时、空响应或启动异常时取消底层 HTTP 请求并切换；
- 实现 `CLOSED / OPEN / HALF_OPEN` 三态熔断；
- 半开状态仅允许一个探测调用；
- 调用结束、取消和异常均必须释放半开探测许可；
- Trace 与 Trust Provenance 记录最终实际模型和必要的 Fallback 原因。

#### 边界

- 第一版可与 Ragent 一致使用进程内健康状态，但必须明确它不跨节点共享；
- 本轮不把熔断状态迁移到 Redis，不实现分布式熔断；
- Fallback 不得静默改变模型能力，例如从支持结构化输出的模型降级到不满足契约的模型。

#### 验收标准

- 首选模型启动失败、首包超时和空响应有回归测试；
- Fallback 后前端和 Trace 显示最终实际模型；
- 连续失败进入 OPEN，冷却后只有一个 HALF_OPEN 探测；
- 用户取消能中止当前真实上游请求。

### 5.6 持久化会话摘要

#### 目标

在保留最近 N 轮原始消息的同时，以持久摘要保存更早上下文，控制 Token 成本并支持长会话。

#### 改造内容

- 摘要表保存会话、用户、摘要文本、覆盖到的最后消息 ID、模型与 Prompt 版本；
- 加载时并行或一次性读取最新摘要和最近 N 轮原始消息；
- 达到轮次或 Token 阈值后异步压缩；
- 新摘要合并旧摘要并保留原始历史重叠窗口；
- 对照 Ragent 使用 Redis 锁防止重复压缩；若本轮尚未进入多实例运行，可在对应阶段再启用；
- 摘要失败时继续使用旧摘要；
- 引用显示标记、内部 Trace 和不可信工具输出不得直接写入摘要；
- 继续沿用当前“弱依据回答不进入历史”的原则，不另建摘要可信度状态机。

#### 验收标准

- 长会话 Token 使用受控且关键上下文保留；
- 并发触发只产生一个有效新摘要；
- 话题切换不会错误继承旧主题；
- 无依据回答不会作为确定事实污染后续问答；
- 摘要模型失败不阻塞正常聊天。

## 6. 后续按需对照，不纳入本轮核心优化

### 6.1 Redis 跨节点 SSE 取消

参考 Ragent 的“Redis 标记 + Pub/Sub + 执行节点本地取消句柄”协议：

```text
任意 API 接收取消请求
→ 写入带 TTL 的取消标记
→ 发布取消事件
→ 所有 API 收到通知
→ 真正执行任务的节点取消上游 HTTP 请求
→ 只执行一次持久化和 SSE 收尾
```

该功能只有在实际运行多个 API 实例时才实施；单实例阶段继续使用现有取消机制，不提前引入 Redis 协调。

### 6.2 Redis 全局模型并发控制

参考 Ragent 的公平排队语义：

- Redis ZSET 维护全局等待顺序；
- 全局序号保证稳定排队；
- 可过期信号量保护模型并发；
- Lua 原子完成队首判断、抢占和状态变更；
- Pub/Sub 提醒等待者，定时轮询作为恢复路径；
- 用户取消、等待超时和节点退出都必须清理队列项；
- 许可使用租约，节点崩溃后可以自动回收。

该能力与 Ragent 对应，但开发复杂度较高。本轮不实施；只有实际出现多个 API 共同竞争模型额度的需求时再对照移植。

### 6.3 多实例部署验证

完成核心改造后可以做一次最小部署验证，但不建设额外的集群管理能力：

```text
2 个 API 实例
2 个 RocketMQ Consumer 实例
共享 PostgreSQL
共享 Redis
共享 S3 兼容对象存储
共享 Milvus
```

验证场景至少包括：

- API A 上传，Consumer B 处理，API B 查询和预览；
- 停止一个 API 后新请求继续处理；
- 停止一个 Consumer 后消息由另一个 Consumer 处理；
- 同一消息重复投递不产生重复有效索引；
- 事务二次确认丢失后正确回查；
- 所有进程重启后任务、文档、会话、引用和 Trust 结果仍存在。

只有这些验证通过后，才能描述为“支持多实例部署与横向扩展”；不能仅凭 Docker Compose 中存在多个容器就宣称高可用。

## 7. 本轮不优化的附加方面

### 7.1 任务与运行管理页面

Ragent 有相应管理能力，但本轮不新增管理页面。现有页面仅在字段发生变化时做必要兼容，不增加以下功能：

- 文档任务当前阶段和执行节点；
- 重试次数、下次重试时间和失败分类；
- 死信状态与人工恢复；
- 解析、切块、Embedding、写入和验证耗时；
- RocketMQ 消费积压及 Consumer 状态；
- 模型候选、首包耗时、Fallback 和熔断状态；
- 不确定完成任务的人工核对入口。

### 7.2 细粒度知识权限

本轮维持现有用户所有权隔离和管理员角色，不增加组织、部门、知识库成员、文档级 ACL 等新业务模型。

## 8. 明确暂不优化的方面

### 8.1 不建设通用 ReAct Agent 框架

Ragent 参考提交的 `agent` 模块尚无实际 Java 主代码。本项目已有 NaiveRAG、ChainOfRAG、DeepSearch 和动态路由，当前没有必要为对齐宣传名词而重写 Agent 框架。

### 8.2 不接入演示型 MCP

天气、票务等示例工具不能证明企业知识场景落地，而且会引入参数确认、权限、幂等和审计负担。只有出现真实业务动作并具备完整治理要求时，再单独分析 MCP。

### 8.3 不引入知识图谱检索

当前应先提高 Dense、BM25、RRF 和多文档重排在既有业务评测集上的覆盖。没有对照实验前，不增加 LightRAG、Neo4j 或 GraphRAG 通道。

### 8.4 不建设可视化入库 Pipeline

Ragent 自身的知识库 Pipeline 模式在参考提交中仍暂停。当前固定入库链路更容易保证事务、幂等和索引版本一致，不实施拖拽节点、动态脚本和条件编排。

### 8.5 不拆微服务

继续采用模块化单体：API 与 Consumer 可作为不同进程和不同副本运行，但共享领域代码和契约。当前不拆用户、会话、知识库、模型和 Trace 独立服务。

### 8.6 不继续扩充 Provider 数量

项目已经支持较多 LLM、Embedding 和向量库。下一阶段关注候选路由、Fallback、首包、熔断和审计，不再以新增供应商名称作为成果。

### 8.7 不继续扩张 Trust Layer 规则范围

现有 Claim、Evidence、Citation Span、数字/日期/条件一致性、时效、风险、语义蕴含和 Provenance 已形成核心差异。工程化阶段只维护契约和修复回归，不持续增加新规则类型。

### 8.8 不大规模重做前端视觉

当前工作台已覆盖知识库、文档、问答、引用、核验和 Trace。只补任务管理、死信恢复、模型 Fallback 和多实例故障状态，不进行脱离工程目标的视觉重构。
